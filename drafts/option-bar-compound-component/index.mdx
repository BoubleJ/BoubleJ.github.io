## 1. 기존 옵션바의 문제

- 리스트 페이지마다 옵션바를 따로 구현했습니다. 조사해 보니 옵션바 구현이 15곳이었고, 공통 컴포넌트가 두 개(`OptionBar`, `ContentListSortBase`)와 상세 필터 패널이 따로 있었습니다.
- 같은 기능이 페이지마다 다른 자리에 놓였습니다. 정렬 드롭다운은 오른쪽 끝(검색 키워드, 무료쿠폰), 리스트타입 앞(만화, 소설, 웹툰), 오른쪽 세 요소 중 두 번째(서재)에 왔습니다.
- 정렬 선택과 선택 적용 시 url을 바꾸는 코드를 페이지마다 반복했습니다.

## 2. 컴파운드 컴포넌트로 조합한 이유

- 페이지별 배치를 표로 정리해 보니 개수는 항상 왼쪽 끝, 필터는 항상 오른쪽 끝이었습니다. 그 사이의 요소는 페이지마다 종류와 순서가 달랐습니다.
- 그래서 하위 컴포넌트가 자기 자리를 정하지 않고, 사용처가 필요한 요소만 순서대로 나열하는 방식을 택했습니다.
- 왼쪽과 오른쪽을 나누는 방법으로 `OptionBar.Spacer`와 `OptionBar.Group`을 검토했습니다.
- 새 옵션바를 쓸 페이지를 다시 확인하니 모두 개수만 왼쪽에 있고 나머지 요소는 오른쪽에 있었습니다. 그래서 배치용 컴포넌트를 따로 만들지 않고 `OptionBar.Count`에 `mr-auto`를 줬습니다. 개수 뒤의 요소는 모두 오른쪽에 붙습니다.
- 나중에 요구사항이 바뀌어 왼쪽에 개수 말고 다른 요소가 추가되면 그때 배치 방식을 다시 수정하기로 판단했습니다.
- 상세 필터 열림 상태는 루트가 context로 갖습니다. 정렬 드롭다운을 열거나 리스트타입 버튼을 누르면 상세 필터가 닫히는 연결을 사용처에서 하지 않아도 됩니다.
- 편집 버튼처럼 한 페이지에만 있는 요소는 `children`으로 옵션바 안에 바로 넣습니다.

## 3. 공통 처리와 페이지별 처리를 나눈 기준

### 3-1. 처음 판단: url 처리는 사용처에 둔다

- 대상 페이지의 정렬 핸들러를 조사하니 url을 바꾸는 방식이 페이지마다 달랐습니다.

| 페이지 | 정렬 변경 시 동작 |
| --- | --- |
| 웹툰 장르 | `sort`, `page=1`로 `router.replace` |
| 만화 리스트 | 만화 전용 경로 함수로 url을 만들어 `router.replace` |
| 무료쿠폰 | 스크롤 위치 초기화, 정렬값 세션스토리지 저장 후 `router.replace`, `page` 갱신 없음 |

- 옵션바 안에서 처리하려면 바꿀 쿼리 key, `page=1` 초기화 여부, 덮어쓰기 방법까지 설계해야 했습니다. 사용처가 웹툰 하나뿐인데 API가 복잡해져서 `onChange`, `changeFilter`를 외부에서 받았습니다.

### 3-2. url 처리는 내부에서 하고 세션스토리지 저장 같은 페이지별 요구사항은 핸들러로 받는다

- 리스트 페이지마다 같은 url 처리를 반복하고 있었습니다. 기존 쿼리를 유지한 채 값을 바꾸고 `page=1`로 `router.replace`하는 코드입니다.
- 그래서 정렬 선택과 선택 적용 시 url 처리를 옵션바 안으로 옮겼습니다. 경로는 `usePathname()`으로 현재 path를 씁니다.
- 세션스토리지 저장처럼 페이지마다 다른 요구사항은 외부 핸들러로 받기로 판단했습니다. 정렬 선택은 `onChange`, 선택 적용은 `onApply`로 받고 url 갱신보다 먼저 호출합니다.

| 페이지 | 페이지별 요구사항 | 받는 핸들러 |
| --- | --- | --- |
| 무료쿠폰 | 정렬 변경 시 쿠폰 종류별 정렬값을 세션스토리지에 저장 | `onChange` |
| 만화 리스트 | 선택 적용 시 적용한 필터를 세션스토리지에 저장 | `onApply` |

### 3-3. 필터 선택값과 개수

- 처음에는 `currentFilter`와 `count`를 prop으로 받았습니다.
- `groups`에 쿼리스트링 key와 옵션이 모두 있어서, 현재 url에서 그룹 옵션에 있는 값만 골라 체크 상태와 개수를 내부에서 계산하도록 바꿨습니다.
- 그 결과 웹툰 전용 파싱 함수와 개수 계산 함수가 필요 없어져서 지웠습니다.

### 3-4. 선택 규칙

- 처음에는 공통 패널 안에 "같은 key는 하나만, `eventTypes`는 여러 개" 규칙을 넣었습니다.
- 사용처마다 규칙이 달라서 외부로 뺐습니다. 만화는 작품형식 그룹이 key가 다른데도 하나만 선택되는 규칙이 있었습니다.
- 최종적으로 그룹마다 `isMultiple` boolean 하나로 표현했습니다. 만화처럼 key가 다른 그룹은 url은 같은 key로 두고 api 요청 시 가공하면 된다고 판단했습니다.

### 3-5. 외부 주입으로 남긴 것

- 정렬 드롭다운의 처음 선택값(`defaultOption`)은 prop으로 둡니다. 무료쿠폰처럼 세션스토리지 정렬값이나 페이지별 기본값을 쓰는 화면이 있어서입니다.
- 리스트타입 클릭 시 `urlChanged` 앱브릿지는 검색 작품과 키워드에서 아직 쓰므로 앱 채널일 때만 호출하도록 남겼습니다.

## 4. 상세 필터 설계

### 4-1. 그룹 상수 형태

1. 기존 웹툰 상수는 옵션 배열과 그룹 객체 두 개로 나뉘어 있었습니다. 그룹 객체에 `maxSelection`, `hidden`이 있었습니다.
2. `maxSelection`과 `hidden`을 빼고 `isMultiple`로 바꿨습니다.
3. 옵션과 그룹을 상수 하나로 합쳤습니다.
4. 배열에서 `name`을 key로 하는 객체로 바꿔, 같은 그룹을 두 번 적으면 TypeScript가 에러를 내게 했습니다. `FilterGroups<T>` 타입으로 key 누락과 그룹별 옵션 값도 검사합니다.

### 4-2. 상세 필터를 createPortal로 옵션바 아래에 그린 이유

- `OptionBar.DetailFilter`를 따로 두지 않기로 했습니다. 필터 버튼이 있으면 상세 필터가 있는 것이 당연해서 `OptionBar.Filter` 하나가 버튼과 패널을 함께 그립니다.
- 그런데 `OptionBar.Filter`는 옵션바 줄 안에 놓입니다. 옵션바 줄에는 `z-option-bar`(z-index 2)가 있어서 줄 안의 요소는 이 줄 안에서만 z-index를 비교합니다.
- 패널과 딤을 줄 안에 그대로 그리면 딤(z-index 1)이 같은 줄의 개수, 정렬 드롭다운, 리스트타입 버튼 위에 그려져 옵션바 줄까지 어둡게 덮습니다.
- 딤이 옵션바 줄 아래에 깔리려면 패널과 딤이 옵션바 줄 바깥, 줄의 형제 위치에 있어야 합니다. 이를 위해 세 가지 방법을 비교했습니다.

| 방법 | 사용처 코드 | 문제 |
| --- | --- | --- |
| 1. 버튼과 패널을 나눈다 | `<OptionBar.Filter>`는 줄 안에, `<OptionBar.FilterPanel>`은 줄 밖에 적음 | 필터를 쓰는 페이지마다 둘을 짝으로 적어야 하고 한쪽만 적는 실수가 생김 |
| 2. 루트가 필터 설정을 받는다 | `<OptionBar filter={...}>`에 설정을 넘기고 `OptionBar.Filter`는 버튼만 그림 | 같은 기능의 설정이 루트와 children 두 곳에 나뉨. `OptionBar.Filter`를 빼먹으면 여는 버튼이 없는 패널이 생김 |
| 3. portal로 줄 밖에 그린다 | `<OptionBar.Filter groups={...} />` 하나만 적음 | 루트에 패널 자리 `<div>`와 그 요소를 담는 state가 생김 |

- 3번을 택했습니다. 필터 설정이 `OptionBar.Filter` 한 곳에 모이고, 필터가 없는 페이지는 `OptionBar.Filter`를 빼기만 하면 패널도 그려지지 않습니다. 늘어나는 코드는 루트 안에만 있어서 사용처는 몰라도 됩니다.
- portal 대상은 `document.body`가 아니라 옵션바 줄 바로 아래의 빈 `<div>`입니다. 패널이 옵션바 너비만큼 줄 바로 아래에 붙어야 하고, 화면 아래 끝까지의 높이를 계산하는 기준도 이 위치이기 때문입니다. 정렬 드롭다운 메뉴는 Radix가 트리거 위치를 계산하므로 `document.body`로 portal하는 것과 다릅니다.

### 4-3. 패널 자리를 useRef가 아니라 callback ref와 state로 받는 이유

```tsx
const [detailFilterContainer, setDetailFilterContainer] = useState<HTMLDivElement | null>(null)

<div ref={setDetailFilterContainer} />
```

- `createPortal`은 이미 존재하는 DOM 요소가 있어야 부를 수 있습니다. 첫 렌더에서는 패널 자리 `<div>`가 아직 DOM에 붙지 않아서 대상이 `null`입니다.
- `useRef`로 받으면 요소가 붙어도 리렌더가 일어나지 않아 `OptionBar.Filter`가 계속 `null`을 보고 패널을 그리지 못합니다.
- `useState` setter를 callback ref로 넘기면 요소가 DOM에 붙는 시점에 state가 바뀌고 다시 렌더됩니다. 다음 렌더에서 패널이 portal로 그려집니다.
- 패널은 닫힌 상태로 시작하므로 한 번 늦게 그려져도 화면은 달라지지 않습니다.

공식 문서

| 문서 | 확인한 내용 |
| --- | --- |
| [React ref callback](https://react.dev/reference/react-dom/components/common#ref-callback) | `ref`에 객체 대신 함수를 넘길 수 있습니다. DOM이 붙으면 요소와 함께 호출하고, 떨어지면 cleanup을 부르거나 `null`로 다시 호출합니다 |
| [이전 React Hooks FAQ: How can I measure a DOM node?](https://legacy.reactjs.org/docs/hooks-faq.html#how-can-i-measure-a-dom-node) | 객체 ref는 `current` 값이 바뀌어도 알려주지 않아서 callback ref를 썼다고 설명합니다 |
| [React createPortal](https://react.dev/reference/react-dom/createPortal) | portal 대상 요소를 `popupContainer` state에 담고, 값이 생긴 뒤에만 `createPortal`을 부르는 예시가 있습니다. 이 예시는 요소를 callback ref가 아니라 `useEffect`에서 받습니다 |

라이브러리 사례

| 라이브러리 | 같은 방식을 쓰는 곳 |
| --- | --- |
| Radix UI Popper | 기준 요소와 메뉴 요소를 `useState`에 담고 ref로 setter를 넘깁니다. 정렬 드롭다운의 메뉴 위치 계산이 이 방식으로 동작합니다 |
| [Floating UI](https://floating-ui.com/docs/react) | `ref={refs.setReference}`, `ref={refs.setFloating}`처럼 callback ref를 씁니다. 조건부 렌더링 등으로 요소가 바뀌어도 위치를 다시 계산하기 위해서라고 설명합니다 |
| Radix UI Portal | portal 대상을 `container` prop으로 받고, 대상 요소가 없으면 `null`을 반환합니다. `DetailFilter`가 `detailFilterContainer`가 없으면 `null`을 반환하는 처리와 같습니다 |

주의할 점

- portal 안에서 일어난 이벤트는 DOM 트리가 아니라 React 트리를 따라 전파됩니다. 지금은 옵션바 줄에 클릭 핸들러가 없어서 문제가 생기지 않습니다.
- 상세 필터 바깥 클릭 판정(`useOutsideClick`)은 DOM 경로 기준이라 이 전파 방식의 영향을 받지 않습니다.

### 4-4. 체크박스 너비

1. **시안의 규칙**: 시안은 그룹의 옵션 개수에 따라 체크박스 칸 간격이 다릅니다. 옵션이 3개인 그룹(만화의 이용방법, 작품형식)은 81px 간격으로 한 줄에 놓입니다. 그 밖의 그룹은 122px 간격으로 놓습니다.

2. **개수 분기 없이 구현할 수 있는지 검토**: 옵션 개수를 명시적으로 나누지 않고 flex나 grid 하나로 대응할 수 있는지 확인했습니다. 시안과 똑같이 그리려면 어디선가 개수를 구분해야 했습니다.
   - 두 간격(81px, 122px)이 한 칸 너비의 배수 관계가 아니라서 grid 하나로 두 위치를 함께 맞출 수 없습니다.
   - `grid-cols-2`, `grid-cols-3`, `auto-fit`처럼 컨테이너 너비를 나누는 방식은 칸 수가 옵션 개수가 아니라 화면 너비로 정해집니다. 화면이 넓어질수록 간격이 벌어집니다.
   - CSS 자식 개수 선택자(`:has(> :nth-child(3):last-child)`)로 바꿔도 개수를 구분하는 것은 같고 클래스만 길어집니다.

3. **디자인팀과 협의할지 검토**: 분기를 없애려면 모든 그룹을 같은 간격으로 통일해야 했습니다.
   - 모든 그룹을 3열로 맞추면 2개짜리 그룹 오른쪽이 비고 "최근 1주 신작"처럼 긴 문구가 다음 칸과 겹칩니다.
   - 모든 그룹을 2열로 맞추면 3개짜리 그룹이 2개, 1개로 나뉘어 한 줄이 늘어납니다.
   - 이 방향으로 디자인팀과 협의하려 했습니다. 하지만 시안을 다시 보니 옵션이 2개일 때와 3개일 때 너비를 고정한 배치가 더 보기 좋았습니다. 그래서 시안 그대로 구현하기로 판단했습니다.

4. **최종 구현**: 분기는 옵션이 3개인지 하나로 줄이고, 칸 너비 값은 CSS 변수 하나에서 계산합니다.

```tsx
<div
  className={cn(
    'grid flex-1 items-start gap-y-5 [--option-width:122px]',
    isThreeOptions
      ? 'grid-cols-[repeat(3,calc(var(--option-width)*2/3))]'
      : 'grid-cols-[repeat(auto-fill,var(--option-width))]',
  )}
>
```

- 옵션이 3개인 그룹은 122px의 2/3인 약 81px 칸 3개로 한 줄에 놓습니다.
- 그 밖의 그룹은 122px 칸을 체크박스 영역 너비만큼 만들고 넘치면 줄바꿈합니다(`auto-fill`). 4개짜리 그룹을 따로 분기하지 않아도 됩니다. 375px 화면에서는 2개씩 두 줄로 놓이고 넓은 화면에서는 한 줄로 놓입니다.
- 2개짜리 그룹은 남는 칸을 비워 두므로 화면이 넓어져도 간격이 벌어지지 않습니다.

## 5. 마치며
