서버 컴포넌트에서 `redirect()`를 호출했을 때 응답이 307이 되는 경우와 200이 되는 경우를 정리한다. 기준 버전은 Next.js 14 App Router와 React 18이다.

## redirect()의 동작

서버 컴포넌트에서 `redirect()`를 호출하면 리다이렉트 에러가 throw되고 해당 라우트 세그먼트의 렌더링이 중단된다. Next는 이 에러를 잡아 리다이렉트로 처리한다. 처리 방식은 에러가 발생한 시점에 응답 헤더가 이미 나갔는지에 따라 달라진다.

- 응답 헤더를 보내기 전이면 상태 코드를 307로 바꾸고 `Location` 헤더를 붙여 응답한다.
- 응답 헤더를 보낸 뒤이면 상태 코드를 바꿀 수 없다. 응답 본문에 리다이렉트 정보를 실어 보내고 클라이언트가 이동을 처리한다.

## 307 응답과 200 응답의 차이

| 구분 | 307 | 200 (응답 본문으로 리다이렉트) |
|---|---|---|
| 리다이렉트를 처리하는 곳 | 브라우저 네트워크 단계 | 클라이언트 JS (Next 클라이언트 라우터) |
| 중간 페이지 렌더링 | 브라우저가 HTML을 받지 않아 그리지 않는다 | 리다이렉트를 호출한 세그먼트의 상위 레이아웃까지 그린다 |
| 이동 시점 | 응답을 받으면 바로 이동한다 | JS 로드와 hydration이 끝난 뒤 이동한다 |
| 요청 과정 | 문서 요청(307) → 목적지 문서 요청 | 문서 요청(200) → JS 청크 → 목적지 RSC 요청 |
| 로그와 모니터링 | 307로 기록된다 | 200으로 기록되어 리다이렉트인지 구분되지 않는다 |

307은 서버가 페이지를 보내지 않고 목적지만 알려주는 방식이다. 200은 서버가 페이지를 보내기 시작한 뒤에 목적지를 알려주는 방식이다. 그래서 200일 때는 그 사이에 그려진 레이아웃이 사용자에게 보인다.

## 문서 요청과 RSC 요청

브라우저가 서버에 보내는 요청은 이동 방식에 따라 두 가지로 나뉜다.

### 문서 요청

`window.location` 이동, 주소창 입력, 새로고침, 서버 리다이렉트 응답을 따라가는 경우에 일어난다.

- 브라우저가 페이지를 새로 열고 서버에 HTML을 요청한다.
- 서버는 HTML을 만들어 응답하고 브라우저는 기존 화면을 버리고 받은 HTML로 처음부터 다시 그린다.

### RSC 요청

App Router의 클라이언트 네비게이션(`router.push`, `router.replace`, `<Link>` 클릭)에서 일어난다.

- 페이지를 새로 열지 않고 이미 떠 있는 React 앱 안에서 JS가 `fetch`로 요청한다.
- 요청 url에 `_rsc` 쿼리가 붙고 `RSC` 요청 헤더가 실린다.
- 서버는 HTML 대신 페이지의 React 컴포넌트 트리 데이터(RSC payload)를 응답한다.
- 클라이언트 라우터가 이 데이터로 바뀐 부분만 화면에 반영하고 공통 레이아웃은 유지한다.

### 요청 방식에 따른 redirect() 처리

- 문서 요청: Next가 HTML 렌더링 중 발생한 리다이렉트 에러를 잡아 상태 코드를 307로 바꾼다. 단 Suspense 경계 때문에 응답이 이미 시작됐다면 200이 된다 (아래 내용 참고).
- RSC 요청: 서버는 HTML 렌더링을 거치지 않고 RSC payload만 만든다. 이 경로에는 307로 바꾸는 처리가 없다. 리다이렉트 에러는 "이 세그먼트에서 리다이렉트 에러가 났다"는 정보로 payload에 실려 200으로 응답된다. 클라이언트가 payload를 화면에 반영하는 과정에서 상위 레이아웃을 그리고, 해당 세그먼트 자리에서 에러를 잡아 다시 이동한다.

## Suspense 경계와 스트리밍

### Suspense가 없을 때

Next는 페이지의 비동기 작업(await)이 끝날 때까지 HTML을 한 바이트도 보내지 않는다. 그 사이 상위 레이아웃 HTML도 서버 메모리에서만 만들어진다. 비동기 작업 후 `redirect()`가 throw되면 Next는 만들던 HTML을 버리고 307과 `Location` 헤더만 응답한다. 브라우저는 HTML을 받지 않으므로 중간 페이지가 화면에 그려지지 않는다.

### Suspense가 있을 때

Suspense 경계가 있으면 Next는 경계 바깥 HTML을 먼저 스트리밍으로 보낸다. 경계 안쪽은 fallback으로 채운다. 첫 바이트를 보내는 순간 상태 코드 200과 응답 헤더가 확정된다.

경계 안쪽에 있는 컴포넌트는 직접 await하지 않더라도 자식이 suspend하면 함께 기다린다. 가장 가까운 Suspense 경계 단위로 내용이 함께 보내지기 때문이다. 예를 들어 루트 레이아웃이 children을 Suspense로 감싸면 하위 레이아웃과 페이지가 모두 그 경계 안에 들어간다.

이 상태에서 페이지가 `redirect()`를 호출하면 아래 순서로 처리된다.

1. 서버가 경계 바깥 HTML을 보낸다. 경계 자리에는 fallback이 들어가고 상태 코드 200이 확정된다.
2. 페이지의 await가 끝나고 리다이렉트 에러가 throw된다. React는 이 경계를 서버에서 에러가 난 경계로 표시한다. 이 경계를 클라이언트에서 다시 렌더링하라는 표시(`data-dgst="NEXT_REDIRECT;..."`가 붙은 `<template>`)를 HTML에 보낸다.
3. 같은 응답 안에 RSC payload가 실려 온다. 에러를 throw하지 않은 상위 레이아웃은 정상 렌더 결과로 들어 있고 리다이렉트를 호출한 세그먼트만 에러로 들어 있다.
4. 브라우저가 hydration하면서 이 경계를 RSC payload로 클라이언트 렌더링한다. 상위 레이아웃이 그려지고 해당 세그먼트 자리에서 리다이렉트 에러가 throw된다.
5. Next가 각 세그먼트를 감싸 둔 리다이렉트 에러 경계가 이 에러를 잡고 클라이언트 라우터로 목적지에 이동한다.
6. 목적지 RSC 응답이 오면 화면이 바뀐다. 4번부터 6번까지 상위 레이아웃이 화면에 노출된다.

JS가 동작하지 않는 환경을 위해 Next는 스트림에 `<meta http-equiv="refresh">` 태그도 함께 넣는다. 307이면 지연을 1초, 308이면 0초로 설정한다.

## 미들웨어 리다이렉트

미들웨어는 페이지 렌더링 전에 실행된다. 미들웨어가 리다이렉트를 응답하면 페이지 컴포넌트는 실행되지 않는다.

- 문서 요청이면 브라우저가 리다이렉트 응답을 따라 목적지 문서를 요청한다.
- RSC 요청이면 클라이언트 라우터의 `fetch`가 리다이렉트를 따라가 목적지의 RSC payload를 받는다.

두 경우 모두 중간 페이지의 데이터가 만들어지지 않으므로 중간 페이지의 레이아웃이 그려지지 않는다.

## 정리

중간 경유 페이지의 레이아웃 노출 없이 리다이렉트하려면 아래 둘 중 하나를 만족해야 한다.

1. 문서 요청으로 이동하고, 리다이렉트를 판단하는 서버 컴포넌트가 Suspense 경계 안에서 판단하지 않도록 한다. 리다이렉트 판단보다 위쪽에 Suspense 경계를 두지 않는다.
2. 리다이렉트 판단을 미들웨어에서 한다. 이 경우 요청 방식과 관계없이 페이지가 렌더링되지 않는다.

서버 컴포넌트의 리다이렉트가 RSC 요청이나 Suspense 경계 안에서 일어나면 응답은 200이 되고, 클라이언트가 상위 레이아웃을 그린 뒤에 이동한다.
