## 요약

라우터 캐시에 이전 페이지가 없는 상태에서 뒤로가기를 하면 Next.js가 이전 페이지를 서버에 다시 요청한다. React는 popstate 중의 렌더링을 동기로 처리하므로, Suspense 경계가 없으면 응답이 올 때까지 아무것도 commit하지 못하고 화면이 멈춘다. 이 상태에서 스크롤 등으로 상태가 바뀌면 같은 렌더링이 반복해서 suspend되고, 그 횟수가 100을 넘으면 응답이 도착하는 시점에 React #482 에러가 발생한다. 에러는 `error.tsx`가 받아 500 화면을 그린다.

Suspense 경계 안에서 suspend되면 React가 fallback을 commit하므로 반복 횟수가 쌓이지 않고 에러도 발생하지 않는다. 대신 응답을 기다리는 동안 fallback이 노출된다.

## 환경

- Next.js 14.2.35 (App Router)
- React 18.3.0-canary-178c267a4e-20241218 (Next.js에 포함된 버전)

## 증상

1. 뒤로가기를 누르면 url은 이전 페이지로 바뀌지만 화면에는 현재 페이지가 그대로 남는다.
2. 서버 응답이 올 때까지 클릭이나 스크롤에 따른 화면 변화가 반영되지 않는다.
3. 응답을 기다리는 동안 계속 스크롤하면 응답이 도착하는 시점에 아래 에러가 발생하고 500 화면이 그려진다.

```
Minified React error #482
async/await is not yet supported in Client Components, only Server Components. ...
```

에러 메시지는 async Client Component에 대한 안내지만, 이 경우에는 async Client Component와 관계가 없다.

## 발생 조건

아래 조건이 모두 맞아야 에러 화면이 그려진다.

1. Next.js 페이지끼리 클라이언트 네비게이션(`Link`, `router.push`)으로 이동한 히스토리가 있다.
2. 뒤로가기 대상 페이지가 라우터 캐시에 없다. 아래 두 경우에 캐시가 없다.
   - `router.refresh()`를 호출해 라우터 캐시가 비워진 경우
   - 페이지를 새로 불러온 경우(새로고침, `location.reload()`). 라우터 캐시는 새로 시작되지만 브라우저 히스토리에는 이전 문서에서 `pushState`로 만든 항목이 남는다.
3. 렌더링된 Suspense 경계가 없는 상태에서, 응답을 기다리는 동안 상태 업데이트가 100번 넘게 일어난다. 스크롤 위치를 상태로 갖는 훅이 있으면 터치 스크롤 약 2초(약 120프레임)에 해당한다.

응답이 빠르거나 그 사이 상태 업데이트가 적으면 잠깐 멈췄다가 정상으로 그려진다.

## 원인

### 1. 캐시 없는 뒤로가기에서 suspend

뒤로가기를 누르면 Next.js가 `startTransition` 안에서 `ACTION_RESTORE`를 dispatch한다(`app-router.js`). restore는 기존 라우터 캐시로 화면을 그리는데, 이전 페이지의 캐시 노드가 없으면 `layout-router.js`가 RSC를 요청하고 `use(lazyData)`로 응답을 기다리며 suspend한다.

`router.refresh()`는 빈 캐시 노드를 새로 만들고 현재 페이지만 다시 채운다(`refresh-reducer.js`, 주석: `router.refresh() has to invalidate the entire cache`). 그래서 직전에 방문한 페이지의 캐시도 함께 사라진다.

### 2. React가 popstate 중의 트랜지션을 동기로 렌더링

React는 popstate 이벤트 중에 예약된 트랜지션을 동기로 렌더링한다. 브라우저가 popstate 직후 스크롤 위치와 폼 상태를 복원하기 때문이다(React PR #26025).

이때 `upgradePendingLaneToSync`는 트랜지션 lane을 SyncLane으로 바꾸지 않는다. SyncLane을 새로 추가하고 트랜지션 lane에 묶는다(entangle). 이후 SyncLane을 렌더링할 때마다 뒤로가기 트랜지션이 함께 렌더링되고, 둘이 함께 끝나야 SyncLane도 끝난다.

```js
root.pendingLanes |= SyncLane;
root.entangledLanes |= SyncLane;
root.entanglements[SyncLaneIndex] |= lane;
```

### 3. Suspense 경계가 없으면 commit하지 않고 기다림

동기 렌더링이 Suspense 경계 없이 suspend되면 React는 fallback을 그릴 수 없다. Concurrent root에서는 에러를 던지지 않고 commit 없이 기다린다(`ReactFiberThrow.js`, "suspend indefinitely without committing"). 렌더링은 `RootDidNotComplete`로 끝나고 SyncLane과 트랜지션 lane이 suspended로 표시된다. 화면에는 이전 페이지가 남는다.

이때 Suspense 경계 없이 suspend된 동기 렌더링 횟수를 `root.shellSuspendCounter`에 1 더한다. 이 값은 commit될 때(`markRootFinished`)만 0으로 초기화된다.

```js
// ReactFiberWorkLoop.js
if (!didSuspendInShell && getSuspenseHandler() === null) {
  didSuspendInShell = true;
}
...
if (didSuspendInShell) {
  root.shellSuspendCounter++;
}
```

### 4. 상태 업데이트마다 같은 렌더링을 반복

1. 스크롤 이벤트 중의 `setState`는 `InputContinuousLane`을 받는다.
2. `markRootUpdated`는 새 업데이트가 들어오면 `root.suspendedLanes`를 비운다. suspend된 렌더링을 다시 시도하기 위해서다.
3. `getNextLanes`가 다음 렌더링 lane을 고른다. `enableUnifiedSyncLane`이 켜져 있어서 `SyncLane | InputContinuousLane | DefaultLane`을 한 묶음으로 고른다.
4. `getEntangledLanes`가 SyncLane에 묶인 뒤로가기 트랜지션 lane을 추가한다.
5. 스크롤 업데이트와 뒤로가기가 한 번에 동기로 렌더링되고, 뒤로가기 쪽이 다시 suspend되어 3번으로 돌아간다. 카운터가 1 오른다.

스크롤 업데이트도 suspend된 렌더링과 같은 묶음이라 commit되지 않는다. 그래서 화면이 멈춘 것처럼 보이고 카운터도 초기화되지 않는다.

```
popstate → Sync + 트랜지션 렌더링 → suspend, commit 없음 (counter 1)
scroll   → setState → suspended 표시 지움
         → Sync + Continuous + 트랜지션 렌더링 → suspend (counter 2)
scroll   → ... (counter 3, 4, ...)
응답 도착 → use(unresolvedThenable) → counter > 100 이면 #482
```

### 5. 응답이 도착하면 에러를 던짐

`trackUsedThenable`은 처음 보는 thenable을 `use()`할 때 카운터가 100을 넘었는지 확인하고, 넘었으면 #482 에러를 던진다(`ReactFiberThenable.js`). 원래는 실수로 만든 async Client Component가 무한히 suspend되는 상황을 잡으려는 장치다.

`layout-router.js`는 응답이 도착하면 서버 응답을 반영하기 전에 `use(unresolvedThenable)`을 호출한다. 이 thenable이 처음 보는 thenable이므로 이 시점에 검사가 일어난다. 그래서 에러는 스크롤하는 동안이 아니라 응답이 도착한 시점에 기록된다.

## Suspense 경계가 있으면 에러가 발생하지 않는 이유

suspend된 지점 위에 렌더링된 Suspense 경계가 있으면 `getSuspenseHandler()`가 그 경계를 돌려준다. `didSuspendInShell`이 `true`가 되지 않으므로 카운터가 오르지 않는다.

1. 동기 렌더링이 경계 안에서 suspend되면 React가 경계의 fallback을 그리고 commit한다.
2. commit되면 `markRootFinished`가 카운터를 0으로 초기화하고, SyncLane이 끝나서 트랜지션 lane과의 묶음도 풀린다.
3. 이후 상태 업데이트는 뒤로가기와 묶이지 않고 따로 렌더링되어 commit된다.
4. 응답이 도착하면 Next.js가 응답을 라우터 캐시에 반영하고 같은 문서 안에서 이전 페이지를 그린다.

#482는 "suspend됐는데 보여줄 fallback도 없고 commit도 못 하는 상태가 계속된다"는 신호다. Suspense 경계가 있으면 이 상태가 만들어지지 않는다.

Suspense가 감싼 범위 밖에서 suspend되는 경우는 막지 못한다. 루트 레이아웃에서 `children`을 감싸도 `children` 바깥에 있는 Provider나 컴포넌트, Next.js 라우터 내부(`app-router`의 `use(state)`)에서 생기는 suspend에는 경계가 없다.

## 루트 `loading.tsx`가 새로고침 후에는 동작하고 refresh 후에는 동작하지 않는 이유

Next.js 14.2는 `loading.tsx`를 라우터 캐시 노드의 `loading` 값으로 들고 있다가 `LoadingBoundary`에 넘긴다. `LoadingBoundary`는 이 값이 있을 때만 `Suspense`를 렌더링한다(`layout-router.js`). 루트 레이아웃 아래에서는 루트 캐시 노드의 `cache.loading`을 쓴다(`app-router.js`).

첫 로드 때는 `create-initial-router-state.js`가 루트 `loading`을 넣는다. 그런데 `router.refresh()`는 루트 캐시를 새로 만들면서 `cache.rsc`만 다시 채우고 `cache.loading`은 채우지 않는다. 그래서 refresh 후에는 루트 `loading.tsx`의 Suspense 경계가 사라진다.

```js
// create-initial-router-state.js: 문서를 처음 불러올 때
const cache = {
  rsc: initialSeedData[2],
  loading: initialSeedData[3], // 루트 loading.tsx
  ...
}

// refresh-reducer.js (Next.js 14.2.35): router.refresh()
const cache = createEmptyCacheNode() // loading: null
...
cache.rsc = rsc
cache.prefetchRsc = null
// cache.loading 은 채우지 않는다
```

이 버그는 Next.js PR #66538("fix 'loading' segment not being copied into new CacheNode")에서 고쳐졌고 v15.0.0에 포함됐다. v14.2 브랜치에는 백포트되지 않았다.

새로고침(F5, `location.reload()`)은 문서를 새로 불러온다. 앞서 refresh로 바뀐 라우터 상태는 남김없이 사라지고, 첫 로드 과정에서 루트 `loading` 값이 다시 채워진다. 그래서 뒤로가기 직전에 마지막으로 일어난 동작이 결과를 정한다.

| 뒤로가기 직전의 마지막 동작 | 루트 `loading` 경계 | 대기 중 스크롤 시 결과 |
|---|---|---|
| 새로고침 | 있음 | 로딩 UI, 에러 없음 |
| refresh → 새로고침 | 있음 | 로딩 UI, 에러 없음 |
| 새로고침 → refresh | 없음 | #482, 500 화면 |
| refresh | 없음 | #482, 500 화면 |

`loading.tsx`가 없으면 어떤 순서든 경계가 없으므로 모두 #482가 발생한다.

이 결과에 따라 `router.refresh()`를 `location.reload()`로 바꾸면 루트 `loading.tsx`의 경계가 유지된다. 반대로 루트 레이아웃에서 `children`을 `<Suspense>`로 직접 감싸면 RSC 응답 안의 실제 요소로 그려지므로 라우터 캐시의 `loading` 값과 관계없이 refresh 후에도 경계가 남는다.

## 재현 방법

### 수동 재현 (크롬)

1. 확장 프로그램이 동작하지 않도록 시크릿 창을 연다. 일부 확장 프로그램은 Page Visibility API를 덮어써서 탭을 전환해도 `visibilitychange`가 발생하지 않는다.
2. DevTools Network 탭에서 Throttling에 Latency 5000ms 사용자 프로필을 만든다.
3. Next.js 페이지 A에 들어가 `Link`로 페이지 B로 이동한다.
4. 라우터 캐시를 비운다. `router.refresh()`를 호출하는 코드가 있으면 그 동작을 일으키고, 없으면 새로고침한다.
5. Throttling에서 2번의 프로필을 선택한다.
6. 뒤로가기를 누르고 곧바로 2초 넘게 계속 스크롤한다.
7. 응답이 도착하면 500 화면이 그려진다.

### 스크립트 재현 (Chrome DevTools Protocol)

수동 재현은 응답 시간과 스크롤 시점이 맞아야 해서 결과가 매번 다르다. 아래 방식으로 두 가지를 직접 조절했다.

1. Google Chrome을 `--remote-debugging-port`, 임시 `--user-data-dir`, `--incognito`로 실행한다.
2. Node.js의 WebSocket으로 CDP에 연결하고, 저장해 둔 로그인 쿠키를 `Network.setCookies`로 넣는다.
3. A에서 B로 `Link`를 클릭해 이동한다.
4. 라우터 캐시를 비운다.
   - refresh 경로: `window.open`으로 새 탭을 열고 `Target.activateTarget`으로 새 탭과 원래 탭을 차례로 활성화해 `visibilitychange`를 일으킨다.
   - 새로고침 경로: `Page.reload`를 실행한다.
5. `Fetch.enable`로 뒤로가기 대상의 `_rsc` 요청을 8초 늦춘다.
6. `history.back()`을 실행하고 `requestAnimationFrame`마다 `scrollBy(0, 8)`을 실행한다.
7. `Runtime.consoleAPICalled`에서 `#482`를 세고, 뒤로가기 직후와 응답 대기 중, 종료 후의 화면을 캡처한다.

Playwright가 띄운 브라우저는 탭을 전환해도 `visibilityState`가 계속 `visible`로 유지되어 `visibilitychange`가 발생하지 않는다. 실제 탭 전환으로 확인하려면 Playwright 대신 Chrome을 직접 띄워 CDP로 조작해야 한다.

### 요청 구분 방법

Network 탭에서 `_rsc`로 필터링하면 RSC 요청을 볼 수 있다.

| 요청 | 구분 방법 |
|---|---|
| prefetch | `Next-Router-Prefetch: 1` 헤더가 있다 |
| `router.refresh()` | `Next-Router-State-Tree` 헤더 값에 `refetch`가 들어 있다 |
| 캐시 없는 뒤로가기 | 뒤로가기 직후 이전 페이지 url로 나간다 |

## 재현 결과

### 스크롤 양에 따른 결과

Suspense 경계가 없는 상태에서 응답 대기 중 프레임마다 8px씩 아래로 스크롤했다.

| 스크롤 시간 | 프레임 수 | 결과 |
|---|---|---|
| 1초 | 61 | 에러 없음 |
| 2초 | 121 | #482, 500 화면 |
| 3초 | 181 | #482, 500 화면 |

휠로 아래로만 스크롤한 경우는 136번 스크롤해도 에러가 나지 않았다. 페이지 끝에 닿으면 `scrollY`가 더 바뀌지 않고, React가 같은 값의 업데이트를 건너뛰어 다시 렌더링하지 않기 때문이다.

### 조건별 결과

응답 대기 중 2.5초 동안 스크롤했다.

| 조건 | 대기 중 화면 | 결과 |
|---|---|---|
| 캐시가 있는 상태에서 뒤로가기 | 즉시 이전 페이지 | 에러 없음 |
| refresh 후 뒤로가기, 스크롤 없음 | 이전 페이지가 멈춘 채 남음 | 응답 후 정상 |
| refresh 후 뒤로가기 | 이전 페이지가 멈춘 채 남음 | #482, 500 화면 |
| 새로고침 후 뒤로가기 | 이전 페이지가 멈춘 채 남음 | #482, 500 화면 |
| `router.refresh()` 대신 `location.reload()` 후 뒤로가기 (`loading.tsx` 없음) | 이전 페이지가 멈춘 채 남음 | #482, 500 화면 |
| 루트 `loading.tsx` 추가, refresh 후 뒤로가기 | 이전 페이지가 멈춘 채 남음 | #482, 500 화면 |
| 루트 `loading.tsx` 추가, 새로고침 후 뒤로가기 | 로딩 UI | 에러 없음, 응답 후 정상 |
| 루트 `loading.tsx` 추가, refresh → 새로고침 후 뒤로가기 | 로딩 UI | 에러 없음, 응답 후 정상 |
| 스크롤 위치를 상태로 갖는 훅 비활성화, refresh 또는 새로고침 후 뒤로가기 | 이전 페이지가 멈춘 채 남음 | 에러 없음, 응답 후 정상 |
| 루트 레이아웃 `children`을 `<Suspense fallback={<표시용 요소/>}>`로 감쌈, refresh 후 뒤로가기 | fallback만 보임 (헤더 포함 전체) | 에러 없음, 응답 후 정상 |
| 루트 레이아웃 `children`을 `<Suspense fallback={null}>`로 감쌈, refresh 또는 새로고침 후 뒤로가기 | 흰 화면 (헤더 포함 전체) | 에러 없음, 응답 후 정상 |

Suspense로 감싼 경우의 화면 변화는 다음과 같다.

1. 뒤로가기를 누르면 즉시 fallback으로 바뀐다. `null`이면 흰 화면이 된다.
2. 서버 응답 시간만큼 fallback이 유지된다. 그동안 스크롤해도 에러가 나지 않는다.
3. 응답이 오면 페이지를 새로 불러오지 않고 같은 문서 안에서 이전 페이지가 그려진다.

루트 레이아웃에서 `children`을 감싸면 첫 로드 때도 서버가 레이아웃과 fallback을 먼저 보내고 페이지 내용을 이어서 스트리밍한다. 첫 로드 HTML에 fallback이 들어 있었고, 페이지 내용이 오기 전에 fallback이 노출되는 것을 확인했다. 루트 `loading.tsx`도 첫 로드 때 같은 방식으로 로딩 UI를 먼저 보낸다. 로컬 운영 빌드에서는 첫 로드 때 0.7~1.5초, 개발 배포 환경에서는 0.04~0.2초 동안 보였다.

## 대응 방안

| 방안 | 효과 | 한계 |
|---|---|---|
| 루트 `loading.tsx` 추가 | 새로고침 후 뒤로가기에서는 경계가 동작해 #482가 발생하지 않음 | refresh 후에는 경계가 사라져 막지 못함 (Next.js 14.2). 첫 로드 때도 로딩 UI를 먼저 보내고 스트리밍함 |
| 루트 레이아웃에서 `children`을 `<Suspense>`로 감쌈 | #482가 발생하지 않음. 응답 후 정상으로 그려짐 | 대기 중 화면 전체가 fallback으로 바뀜. 모든 페이지의 첫 로드에서도 fallback을 먼저 보내고 스트리밍함. `children` 바깥과 Next.js 라우터 내부에서 생기는 suspend는 막지 못함 |
| `router.refresh()`를 `location.reload()`로 바꿈 | refresh로 캐시가 비는 경우가 없어짐 | 단독으로 쓰면 새로고침 후 뒤로가기에서 같은 문제가 생김 |
| 루트 `loading.tsx` 추가 + 세션이 바뀐 경우에만 `location.reload()` | 세션이 그대로면 캐시가 유지되어 뒤로가기가 바로 그려짐. 캐시가 없는 경우(새로고침 후, 세션 변경으로 새로고침한 후)에도 로딩 UI가 동작해 #482가 발생하지 않음 | 첫 로드 때 로딩 UI가 잠깐 보일 수 있음. `loading`을 지우는 다른 `router.refresh()` 호출이 있으면 그 이후에는 막지 못함 |
| `router.refresh()` 호출 줄이기 | 캐시가 비는 경우가 줄어듦 | 새로고침 후 뒤로가기는 남음 |
| 스크롤 위치 대신 기준값 통과 여부와 방향만 상태로 갖기 | 스크롤 중 업데이트가 몇 번으로 줄어 #482가 발생하지 않음 | 응답이 올 때까지 화면이 멈추는 현상은 남음. 다른 원인으로 업데이트가 반복되는 경우는 막지 못함 |
| Next.js 15로 업그레이드 | 루트 `loading` 버그가 고쳐짐 | 캐시 없는 뒤로가기의 동기 suspend가 바뀌었는지는 확인하지 않음 |
