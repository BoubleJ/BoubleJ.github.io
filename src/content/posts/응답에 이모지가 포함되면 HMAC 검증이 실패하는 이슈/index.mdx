# 발단

무탈하게 배포하던 도중 500 에러가 발생했습니다.

황급히 롤백해서 큰 일은 없었지만, API도 비즈니스 로직도 건드린 적이 없는데 500 에러가 났다는 게 상당히 의아했습니다.

디버깅해보니 API 에러도, Next 런타임 에러도 아니었습니다. 저희 소스코드 내부에서 직접 `throw`하는 에러였어요.

저희 서비스는 ISMS 인증을 위해 HMAC 유효성 검증을 처리하고 있는데요. 이 검증이 프론트에서도 이루어지고 있고, 그 검증이 실패해서 던진 에러였습니다.

여기서 더 의아해졌습니다. 모든 API가 정상적으로 데이터를 로드하는데 **특정 API 하나에서만** 검증이 깨진다는 게 신기했거든요.

그래서 그 API의 응답을 뜯어봤더니, 다른 API에는 없는 특이점이 하나 있었습니다.

바로 **이모지**를 내려받고 있었습니다. 🎉

# HMAC 응답 검증 구조

원인을 보기 전에 저희가 어떤 검증을 하고 있었는지부터 정리하고 가겠습니다.

## 왜 적용했나

홈 API에서 사용하는 API들은 대부분 보안에 덜 민감한 영역이지만, 향후 개편에서는 REST API에 HMAC 인증을 적용하는 것이 기본 스펙으로 정해질 예정이었습니다. 개편 전에도 지속적인 추가 개발과 ISMS 인증을 진행해야 했기 때문에 미리 HMAC을 적용하게 되었어요.

목적은 이렇습니다. 공격자가 Proxy 툴(Wireshark, Fiddler 등)로 API 응답을 가로챈 뒤 응답 데이터를 원하는 형태로 위·변조해 비정상적인 행위를 취하는 것을 방지하는 것이죠.

## 검증 흐름

서버와 클라이언트가 **같은 재료로 해시를 만들어 비교**하는 구조입니다.

1. 클라이언트: 요청 시 랜덤 토큰을 헤더에 담아 전송
2. 서버: `SHA256(토큰 + MD5(상태코드) + 응답 body)`를 계산해 응답 헤더(`mrblue-authorization`)로 반환
3. 클라이언트: 같은 방식으로 해시를 계산해 응답 헤더 값과 비교

여기서 중요한 전제가 하나 있습니다. 이 구조가 성립하려면 **양쪽이 해싱하는 body가 바이트 단위로 완전히 동일**해야 한다는 것이죠.

이모지가 바로 이 전제를 깨뜨렸습니다.

# 원인

원인은 서버와 클라이언트 양쪽에 하나씩, 총 두 군데였습니다.

## 1. 서버 : 해싱한 body와 실제로 나간 body가 달랐다

Spring Boot(Jackson) 직렬화 과정에서 이모지는 `\ud83c\udf89` 형태로 escape되어 전송되고 있었습니다. 한글 같은 일반 비ASCII 문자는 literal 그대로 나갔기 때문에, 하필 이모지가 포함된 응답에서만 차이가 생긴 것이죠.

그런데 서버의 HMAC 해싱은 AOP에서 수행되고 있었고, AOP 시점의 body는 아직 escape되기 **전**(이모지 literal) 상태였습니다.

즉 서버가 해싱한 문자열과 클라이언트가 실제로 받아보는 바이트가 서로 달랐습니다.

## 2. 클라이언트(axios) : 파싱된 데이터를 다시 직렬화해서 해싱했다

axios는 인터셉터가 실행되는 시점에 이미 `transformResponse`가 응답을 `JSON.parse`한 뒤라, raw 텍스트가 남아있지 않습니다.

그래서 검증 코드는 파싱된 데이터를 `JSON.stringify`로 되돌려서 해싱하고 있었어요.

```ts
const resString = typeof res.data === 'string' ? res.data : JSON.stringify(res.data)
```

문제는 이 round-trip이 **원문을 복원하지 못한다**는 것입니다.

# JSON.parse → JSON.stringify는 왜 원문을 복원하지 못할까

이 부분이 이번 이슈의 핵심이라 조금 더 파봤습니다.

## 1. `JSON.parse`는 표기법 정보를 버린다

`"\ud83c\udf89"`와 `"🎉"`는 JSON 텍스트에서 **같은 문자열 값의 두 가지 표기법**입니다.

파싱이 끝나고 나면 메모리에는 문자열 값만 남고, "원래 escape로 적혀 있었다"는 정보는 사라집니다. 되살리고 싶어도 되살릴 정보 자체가 없는 것이죠.

## 2. `JSON.stringify`는 필수 escape만 한다

ECMA-262 스펙상 `JSON.stringify`가 escape하는 대상은 다음뿐입니다.

- 큰따옴표 `"`
- 역슬래시 `\`
- 제어 문자(U+0000 – U+001F)
- 짝 잃은 lone surrogate (ES2019+)

유효한 비ASCII 문자는 JSON 텍스트에 literal로 넣는 것이 완전히 합법이므로, 한글이든 이모지든 그대로 출력합니다. Jackson의 `ESCAPE_NON_ASCII` 같은 "비ASCII를 escape하라"는 옵션이 `JSON.stringify`에는 아예 존재하지 않아요.

결과적으로 escape 표기 → parse → stringify를 거치면 **literal 표기로 정규화**됩니다.

## raw 텍스트 ≠ 재직렬화 결과

정리하면, 재직렬화는 raw의 복원이 아니라 "`JSON.stringify`가 선호하는 형식으로의 정규화"입니다. 둘이 일치하는 건 서버 출력이 **우연히** 그 형식과 같을 때뿐이에요.

| 케이스 | raw | 재직렬화 | 일치 |
|---|---|---|---|
| 이모지 escape | `{"t":"\ud83c\udf89"}` | `{"t":"🎉"}` | ❌ |
| 공백·개행(pretty-print) | `{ "a": 1, "b": 2 }` | `{"a":1,"b":2}` | ❌ |
| 숫자 표기 | `{"n":1e2,"m":1.50}` | `{"n":100,"m":1.5}` | ❌ |
| 비ASCII escape | `{"s":"\uc548\ub155"}` | `{"s":"안녕"}` | ❌ |
| 슬래시 escape | `{"u":"a\/b"}` | `{"u":"a/b"}` | ❌ |
| compact + literal + 정규 숫자 표기 | `{"t":"🎉 이벤트","n":100}` | 동일 | ✅ |

백엔드가 compact하게, 한글은 literal로 직렬화하고 있었기 때문에 평소에는 마지막 행처럼 **우연히** 일치했고, escape로 내려오는 이모지만 불일치했던 겁니다.

일치가 보장이 아니라 우연이었으니, 백엔드 직렬화 설정이 조금만 바뀌어도(pretty-print를 켜거나 escape 옵션을 주거나) 언제든 깨질 수 있는 구조였던 셈이죠.

> 해시는 의미가 아니라 바이트를 비교합니다. <br /> 두 표기가 JSON으로서 의미상 동일해도, 바이트가 다르면 검증은 실패합니다.

## 그럼 Fetch 인터페이스는 왜 멀쩡했나

저희는 같은 시기에 axios 래퍼와 fetch 래퍼를 둘 다 쓰고 있었는데, fetch 쪽은 아무 문제가 없었습니다. 이것도 궁금해서 확인해봤어요.

fetch API는 `Response.clone()`으로 body를 여러 번 읽을 수 있습니다. 그래서 fetch 래퍼는 검증용으로 `clone().text()`(raw 텍스트)를, 비즈니스 로직용으로 별도의 `clone().json()`을 각각 읽고 있었습니다.

```ts
const resString = await res.clone().text() // 와이어에 실려온 텍스트 그대로 해싱
```

검증이 파싱과 완전히 독립적이니 escape든 literal이든 **받은 바이트 그대로** 해싱했고, 따라서 애초에 이 문제가 발생할 여지가 없었습니다.

axios만 "인터셉터 시점에 raw가 이미 사라진" 구조 때문에 재직렬화라는 우회로를 탔던 것이죠.

# 해결

## 원칙 : 실제 전송 바이트를 그대로 해싱한다

서버와 클라이언트 양쪽 모두 같은 원칙으로 수렴했습니다.

| 구분 | 문제가 된 방식 | 수정된 방식 |
|---|---|---|
| 서버 | AOP에서 직렬화 **전** 데이터를 해싱 | Servlet Filter(`ContentCachingResponseWrapper`)에서 실제로 나가는 응답 바이트를 해싱 |
| 클라이언트(axios) | 파싱된 데이터를 재직렬화해서 해싱 | `responseType: 'text'` + `transformResponse: []`로 자동 파싱을 끄고, raw 텍스트로 검증한 뒤 수동 `JSON.parse` |

가공된 데이터가 아니라 **실제 전송 바이트**를 기준으로 삼으면 표기 방식과 무관하게 항상 일치합니다.

HMAC을 위해 데이터를 가공하는 게 아니라, 실제로 주고받은 응답을 그대로 해싱해야 한다는 것이 이번 이슈의 핵심이었습니다.

# 한 발 더 : 이 검증은 정말 안전한가

이슈를 해결하고 나니 한 가지 의문이 남았습니다. 애초에 이 검증이 막고자 하는 걸 제대로 막고 있긴 한 걸까요?

## 엄밀한 의미의 HMAC이 아니다

HMAC의 전제는 공격자가 모르는 **공유 비밀키**입니다.

그런데 이 구조에서 키 역할을 하는 랜덤 토큰은 클라이언트가 생성해서 **요청 헤더에 평문으로 전송**됩니다.

위협 모델로 상정한 프록시 도구(Fiddler 등) 기반 중간자 공격을 그대로 따라가 보면 이렇게 됩니다.

1. 응답을 가로챌 수 있는 공격자는 요청도 볼 수 있으므로 토큰을 이미 알고 있습니다.
2. 해싱 공식(`SHA256(토큰 + MD5(상태코드) + body)`)도 프론트 JS에 공개되어 있습니다.
3. 그럼 공격자는 body를 조작한 뒤 같은 공식으로 해시를 재계산해 응답 헤더까지 바꿔치면 검증을 통과시킬 수 있습니다.

조작 주체가 사용자 본인(자기 기기에서 응답을 바꿔 이득을 보려는 경우)이라면 재계산조차 필요 없습니다. 클라이언트에서 실행되는 검증 로직은 클라이언트 소유자가 패치해서 그냥 건너뛸 수 있으니까요.

따라서 이 장치의 실효 범위는 **구조를 분석하지 않은 사람이 프록시에서 응답을 수정하는, 캐주얼한 조작에 대한 방해물** 정도입니다. 실질적 보안 장치로 의존해서는 안 되고, 억제 장치라는 걸 인지하고 사용해야 합니다.

부수적으로 `SHA256(토큰 + 데이터)` 같은 단순 연접 구성은 length extension이라는 알려진 약점이 있는 형태라, 유지하더라도 진짜 HMAC 구성(`HMAC-SHA256`)으로 가는 편이 바람직합니다.

## 클라이언트의 응답 검증은 표준 관행이 아니다

찾아보니 브라우저 프론트엔드가 응답 HMAC을 검증하는 건 보편적인 관행이 아니었습니다.

전송 구간의 위·변조 방지는 TLS(HTTPS)가 담당하는 영역이고, 검증 재료인 토큰이 같은 채널로 오가는 한 암호학적으로 성립하지 않기 때문이죠.

반대로, 클라이언트가 서명·해시를 검증하는 **정당한** 사례들은 하나같이 "검증에 필요한 비밀 또는 신뢰 기준점이 공격자 손에 없다"는 조건을 만족하고 있었습니다.

- **웹훅 서명** ([Stripe](https://docs.stripe.com/webhooks#verify-official-libraries), [GitHub](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries), Slack) — 페이로드를 HMAC으로 서명하고 수신 측이 검증하는 대표 사례입니다. 단, 서버↔서버 통신이고 공유 비밀키가 양쪽 서버에만 존재하기 때문에 성립합니다. 브라우저에는 비밀을 둘 곳이 없죠.
- **SRI (Subresource Integrity)** ([MDN](https://developer.mozilla.org/en-US/docs/Web/Security/Subresource_Integrity)) — 브라우저가 CDN 리소스의 해시를 검증하는 웹 표준입니다. 기대 해시가 신뢰된 출처(자사 HTML)에 고정되어 있고, 검증 대상과 다른 채널로 전달되기 때문에 성립합니다.
- **HTTP Message Signatures (RFC 9421) + Content-Digest (RFC 9530)** — 실제 키를 가진 당사자 간에 사용하는 표준입니다.
- **AWS Signature v4** — 요청 서명의 대표 사례지만 방향이 반대(서버가 클라이언트를 검증)이고, 액세스 키라는 실제 자격증명이 전제입니다.

비밀 없이, 같은 채널의 정보만으로 웹 프론트가 응답을 검증하는 형태는 표준 사례에 없었습니다. 모바일 게임 등에서 치팅 억제용 난독화 장치로 쓰이는 정도이고, 해당 업계에서도 우회 가능한 지연 장치로 취급하더군요.

## 그럼 어떻게 막아야 하나

막고자 하는 위협이 무엇이냐에 따라 답이 갈립니다.

### 1. 네트워크상의 제3자 공격

HTTPS + HSTS로 해결되는 문제입니다.

앱 웹뷰에서 사용자가 프록시 인증서를 설치해 TLS를 우회하는 시나리오까지 막으려면 **인증서 피닝**(certificate pinning — 앱에 서버 인증서·공개키를 내장하고 그것만 신뢰, [OWASP MASTG 권고](https://mas.owasp.org/MASTG/0x04f-Testing-Network-Communication/))이 정석입니다. Fiddler·Charles류 프록시는 자체 인증서를 끼워 넣는 방식이라 피닝에 걸립니다.

### 2. 사용자 본인의 조작

이건 클라이언트 검증으로는 원천적으로 막을 수 없으므로 원칙이 달라집니다.

- **서버를 유일한 진실 공급원으로 삼습니다.** 결제, 성인 인증, 코인 차감, 열람 권한 같은 것들은 클라이언트가 받은 응답과 무관하게 서버가 매번 판정합니다. 클라이언트 표시가 조작되어도 실제로는 아무 일도 일어나지 않는 구조라면, 조작의 실익 자체가 사라집니다.
- 앱이라면 **기기 무결성 증명**(attestation)이 있습니다. [Play Integrity API](https://developer.android.com/google/play/integrity)(Android), [App Attest](https://developer.apple.com/documentation/devicecheck)(iOS)가 기기·앱의 변조 여부를 Google·Apple의 비밀키로 서명해주고 서버가 이를 검증하므로, 클라이언트 조작으로는 위조할 수 없습니다.

### 3. 그래도 응답 서명 검증을 유지하고 싶다면

대칭 해시 대신 **비대칭 서명**으로 전환할 수 있습니다.

서버가 개인키로 서명하고 클라이언트는 내장된 공개키로 검증하는 구조인데요. 공개키는 노출되어도 서명을 위조할 수 없으므로, 공격자가 해시를 재계산해서 우회하는 현재의 결함은 사라집니다.

다만 사용자 본인이 검증 로직 자체를 패치하는 것까지는 막지 못하므로, 네트워크 공격 대응용이라는 한계는 동일합니다.

# 마무리

정리하면 이렇습니다.

첫째, 이번 이슈의 직접적인 원인은 **해싱 대상이 실제 전송 바이트가 아니었다**는 것이었습니다. 서버는 직렬화 전 데이터를, 클라이언트는 파싱 후 재직렬화한 데이터를 해싱하고 있었고, 평소에는 그 둘이 우연히 일치했을 뿐이었습니다.

둘째, JSON은 같은 값을 표현하는 바이트가 여러 가지입니다. escape·공백·숫자 표기·키 순서가 모두 자유롭기 때문에, JSON을 해싱하거나 서명할 때는 "의미가 같으니 바이트도 같겠지"라는 가정을 절대 하면 안 됩니다. 실제로 이건 저희만 겪은 문제가 아니라, [Latacora의 아티클](https://latacora.github.io/blog/2019/07/24/how-not-to/)이나 [RFC 8785(JSON Canonicalization Scheme)](https://datatracker.ietf.org/doc/html/rfc8785)처럼 널리 알려진 함정이었습니다.

셋째, 현재 구조는 캐주얼한 조작에 대한 방해 이상의 보안을 제공하지 않으며, 실질적인 방어선은 TLS(+피닝)와 서버 측 판정입니다. 클라이언트 검증은 있어도 되지만, 그것에 보안을 의존하는 설계는 피해야 한다는 걸 배웠습니다.

## 궁금한 점

지금은 raw 바이트를 해싱하는 방식으로 해결했지만, 서버·클라이언트가 각자 다른 언어·라이브러리를 쓰는 상황에서 이 방식이 항상 최선인지는 아직 잘 모르겠습니다. RFC 8785처럼 정규화(canonicalization)된 JSON을 해싱하는 접근이 더 나은 상황도 있을 텐데, [정규화 접근의 한계를 다룬 글](https://www.da.vidbuchanan.co.uk/blog/signing-json.html)도 있어서 두 접근의 트레이드오프를 좀 더 공부해봐야 할 것 같습니다.

그리고 저희 서비스가 실제로 막아야 하는 위협이 무엇인지(제3자 공격인지, 사용자 본인의 조작인지)부터 팀에서 다시 정리해봐야겠다는 생각이 들었습니다. 그게 정해져야 인증서 피닝이든 비대칭 서명이든 서버 측 판정 강화든 방향이 잡힐 테니까요.
