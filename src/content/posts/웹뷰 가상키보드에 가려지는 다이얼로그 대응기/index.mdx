# 개요

이전 글에서 [shadcn + useOverlay 조합으로 다이얼로그를 만든 과정](/고군분투-다이얼로그-제작-일지/)을 공유드렸는데요.

이번엔 그 다이얼로그를 실제 화면에 붙이면서 만난 문제 하나를 정리해보려 합니다.

작품 상세 페이지에는 별점과 코멘트를 남길 수 있는 **리뷰 작성 다이얼로그**가 있습니다. 별점을 매기고 `textarea`에 코멘트를 적은 뒤 등록하는, 흔한 형태의 입력 다이얼로그입니다.

그런데 QA 과정에서, 사내 앱 웹뷰로 이 화면을 열고 코멘트를 입력하려 하면 이상한 장면이 나왔습니다.

![키보드에가려진다이얼로그](<./키보드에가려진다이얼로그.png>)

**가상키보드가 올라오는 순간 정작 입력해야 할 `textarea`가 사라집니다.** 별점과 취소·등록 버튼만 덩그러니 남고, 코멘트를 적을 공간이 화면에서 증발해버린 거죠.

키보드는 코멘트를 쓰려고 띄운 건데, 그 키보드가 코멘트 입력창을 밀어낸 셈입니다. 사용자 입장에서는 뭘 어떻게 하라는 건지 알 수 없는 상태입니다.

브라우저에서는 멀쩡하고 앱 웹뷰에서만 발생한다는 점이 첫 단서였습니다.

# 원인

## 1. 다이얼로그의 최대 높이 규칙

먼저 사내 디자인 시스템이 다이얼로그에 요구하는 규칙을 다시 확인했습니다.

1. 다이얼로그 높이는 **내부 컨텐츠 내용만큼만** 노출한다
2. 컨텐츠가 많아지면 **디바이스 위아래 여백 50px**을 남기고, 내부 컨텐츠는 **스크롤** 처리한다

이 규칙은 공용 `Dialog`의 `DialogContent`에 `max-height` 한 줄로 구현되어 있었습니다.

```tsx
// src/_common/components/dialog/dialog-components.tsx
// 위아래 50px씩, 총 100px을 뺀 값이 다이얼로그의 상한
'max-h-[calc(100vh-100px)] supports-[height:100dvh]:max-h-[calc(100dvh-100px)]'
```

`max-height`는 어디까지나 **상한**이고, 실제 높이는 컨텐츠가 결정합니다. 컨텐츠가 상한보다 작으면 컨텐츠 크기 그대로 그려지고(요구사항 1), 상한을 넘으면 상한에 걸린 채 내부가 스크롤됩니다(요구사항 2).

여기까지는 의도한 대로 잘 동작하는 코드입니다. 문제는 **`100dvh`가 무엇을 가리키느냐**였습니다.

## 2. 앱이 리사이즈 모드로 동작한다

사내 앱은 플러터로 만들어져 있고, 이 화면을 띄우는 `Scaffold`는 `resizeToAvoidBottomInset: true` 상태입니다.

이게 켜져 있으면 키보드가 올라올 때 키보드가 차지하는 높이(`MediaQuery.viewInsets.bottom`)만큼을 body 높이에서 빼버립니다. 즉 **웹뷰 프레임 자체가 줄어듭니다.**

안드로이드 에뮬레이터(360×640dp)에 CDP를 붙여 실제로 재봤습니다.

```
키보드 닫힘   innerHeight 529   visualViewport 530
키보드 열림   innerHeight 254   visualViewport 255
```

키보드가 뜨자 뷰포트가 **529 → 254**로 절반 아래까지 줄어듭니다. iOS(iPhone 17 Pro 시뮬레이터)도 마찬가지로 **762 → 359** 였습니다.

## 3. 줄어든 뷰포트에서 또 100px을 뺀다

이제 두 사실을 겹쳐놓으면 답이 나옵니다.

`max-height`는 `100dvh - 100px`인데, 리사이즈 모드에서는 이 `100dvh`가 **키보드를 뺀 나머지 영역**을 가리킵니다. 그런데 거기서 위아래 여백 50px씩을 또 떼어냅니다.

| 상태 | 뷰포트 | 다이얼로그 상한 | 컨텐츠 높이 | 실제 높이 |
|---|---|---|---|---|
| 키보드 닫힘 | 529 | 429 | 379 | **379** (컨텐츠 그대로) |
| 키보드 열림 | 254 | **154** | 379 | **154** (상한에 걸림) |

키보드가 뜬 순간 다이얼로그가 쓸 수 있는 높이가 **154px**로 쪼그라듭니다. 여기서 취소·등록 버튼 푸터가 56px를 가져가니 본문에 남는 건 **98px** 남짓입니다.

`textarea`는 152px입니다. 98px 안에 152px가 들어갈 리 없으니 스크롤 영역 밖으로 밀려나고, 스크롤 최상단에 있던 별점만 화면에 남게 된 겁니다.

정리하면 **"위아래 50px 여백" 규칙 자체가 원인**이었습니다. 화면이 넉넉할 땐 다이얼로그를 예쁘게 만들어주는 규칙이, 키보드가 화면의 절반을 먹은 상황에서는 남은 절반에서 또 100px을 빼앗는 규칙이 되어버린 거죠.

## 4. 안내 다이얼로그는 왜 멀쩡했나

같은 공용 `Dialog`를 쓰는데도 리뷰 운영방침 안내 팝업 같은 건 아무 문제가 없었습니다.

당연합니다. **키보드를 띄울 일이 없기 때문입니다.**

입력 요소가 없는 다이얼로그는 뷰포트가 529 그대로이고, 상한 429 안에서 컨텐츠가 잘 그려집니다. 위아래 여백 50px도 정확히 지켜집니다.

즉 이건 다이얼로그 전체의 버그가 아니라, **가상키보드를 띄우는 다이얼로그에서만 드러나는 문제**였습니다. 이 구분이 나중에 해결책을 고를 때 결정적인 기준이 됩니다.

# 그래서 요구사항이 하나 늘었습니다

디자이너와 이야기해 규칙에 조항을 하나 추가했습니다.

3. 가상키보드 노출로 가시 영역이 좁아지면 **여백 처리를 제거하고 가능한 화면에 꽉 차게** 표시한다

키보드가 떠 있는 동안만 상한을 `100dvh - 100px`에서 `100dvh`로 바꿔주면 됩니다. 리사이즈 모드에서는 `100dvh`가 곧 키보드를 제외한 가시 영역이므로, 정확히 원하는 값을 줍니다.

문제는 **"키보드가 떠 있는 동안"을 어떻게 아느냐**입니다.

## visualViewport로는 알 수 없습니다

웹에서 가상키보드를 감지하는 가장 흔한 방법은 레이아웃 뷰포트와 시각 뷰포트의 차이를 보는 것입니다.

```ts
const keyboardHeight = window.innerHeight - window.visualViewport.height
```

키보드가 웹뷰 위에 **덮이는(오버레이)** 방식이라면 레이아웃 뷰포트는 그대로인데 시각 뷰포트만 줄어들기 때문에, 이 차이가 곧 키보드 높이가 됩니다.

그런데 앞서 봤듯이 이 화면은 리사이즈 모드입니다. 웹뷰 프레임 자체가 줄어드니 **둘이 함께** 줄어듭니다.

```
안드로이드  닫힘 inner 529 / vv 530  →  열림 inner 254 / vv 255   (DIFF 항상 -1)
iOS        닫힘 inner 762 / vv 762  →  열림 inner 359 / vv 359   (DIFF 항상  0)
```

DIFF가 **항상 0**입니다. 이 판정식은 절대 발동하지 않아요. JS 기반 키보드 감지는 이 화면에서 쓸 수 없다는 결론이 나왔습니다.

> 사내 프로젝트에도 `use-active-virtual-keyboard`라는 훅이 이미 있었는데, 같은 이유로 이 화면에서는 동작하지 않습니다.

## 그럼 앱을 오버레이 모드로 바꾸면 되지 않나요?

가장 먼저 떠오른 선택지였습니다. 앱에서 `resizeToAvoidBottomInset: false`로 바꾸면 DIFF가 잡히니까요.

하지만 비교해보니 얻는 것보다 잃는 게 많았습니다.

| | 리사이즈 (현행 유지) | 오버레이 |
|---|---|---|
| 키보드 시 `100dvh` | 가시 영역과 동일 | 전체 높이 그대로 |
| 요구사항 3 구현 | CSS 한 줄 | JS로 `visualViewport` 읽어 CSS 변수 주입 + 중앙정렬 오프셋 보정 |
| 키보드 감지 | 불필요 | 필수 |
| 앱 수정 | **불필요** | 필요 |

오버레이로 바꾸면 웹이 키보드 높이를 직접 계산해서 다이얼로그의 위치와 높이를 보정해야 하고, 그 로직을 다이얼로그마다 유지해야 합니다. 게다가 앱 수정은 스토어 배포 주기를 타죠.

반면 리사이즈 모드에서는 **가시 영역이 곧 뷰포트**이므로 `100dvh`가 이미 정답을 알고 있습니다. 웹에서 CSS만으로 끝낼 수 있다는 뜻입니다.

앱은 그대로 두기로 했습니다.

# 해결 — 포커스를 키보드의 프록시로 삼기

`visualViewport`를 못 쓴다면 남은 건 **포커스**입니다.

가상키보드는 입력 요소에 포커스가 갈 때 올라오니까, "다이얼로그 안에 포커스가 있다"를 "키보드가 떠 있다"의 대용품으로 쓰는 거죠. CSS 셀렉터만으로 판정할 수 있다는 것도 큰 장점입니다.

문제는 이 둘이 **완전히 같은 상태가 아니라는 점**입니다. 어떤 셀렉터로 조건을 잡느냐에 따라 결과가 꽤 달라져서, 세 가지 안을 실기기에 올려 하나씩 비교해봤습니다.

## 1안. `:has(textarea:focus)`

가장 직관적인 조건입니다. "다이얼로그 안의 `textarea`에 포커스가 있으면" 상한을 풀어줍니다.

리뷰 작성 다이얼로그에서 키보드를 띄우는 것까지는 완벽하게 동작했습니다. 그런데 **코멘트를 쓰다가 별점을 다시 조정하면** 다이얼로그가 줄었다 커지는 저크가 보입니다.

![1안-리뷰작성](/image/키보드감지-1안-리뷰작성.gif)

50ms 간격으로 샘플링해서 찍어봤습니다.

```
t=100599  inner=254  maxH=254.5px  h=255   focus: TEXTAREA → BUTTON   ← 별점 탭
t=100665  inner=254  maxH=196.9px  h=197   ← 뷰포트는 아직 254인데 상한만 떨어짐
t=100681  inner=268  maxH=184.0px  h=184   ← 최소점
t=100722  inner=383  maxH=184.0px  h=184   ← 뷰포트는 커졌는데 아직 184
t=101012  inner=529  maxH=402.9px  h=379   ← 복귀
```

**255 → 184 → 379**, 약 0.5초 왕복입니다.

원인은 **조건이 바뀌는 시점과 뷰포트가 바뀌는 시점의 어긋남**이었습니다.

별점은 `button`이라 탭하는 순간 포커스가 `textarea`에서 버튼으로 옮겨갑니다. `:has(textarea:focus)`는 **그 프레임에 즉시 false**가 되고, 상한이 곧바로 `100dvh`에서 `100dvh - 100px`로 떨어집니다.

그런데 키보드가 실제로 내려가고 웹뷰가 다시 커지는 건 **애니메이션**이라 300ms쯤 걸려요. 그 사이 뷰포트는 여전히 254입니다.

```
키보드 보임    : ▓▓▓▓▓▓▓▓▓▓░░░░░░   (애니메이션으로 서서히 사라짐)
textarea:focus : ▓▓▓▓▓▓▓▓▓▓|______   (즉시 끊김)
                           ↑ 이 갭이 저크 구간
```

**분자(뷰포트)는 아직 작은데 −100px 페널티만 먼저 적용되는 구간**이 생기는 거죠. `DialogContent`에 `duration-200` 트랜지션이 걸려 있어서 한 프레임 깜빡임이 아니라 눈에 보이는 축소 동작이 됩니다.

버튼은 계속 보이니 기능이 깨지진 않지만, 사용자가 별점을 만질 때마다 다이얼로그가 꿈틀대는 건 그냥 넘길 만한 수준이 아니었습니다.

## 2안. `:focus-within`

그럼 조건을 느슨하게 잡아서, `textarea`든 버튼이든 **내부 어디든 포커스가 있으면** 상한을 풀어주면 어떨까요?

저크는 깔끔하게 사라졌습니다. 포커스가 `textarea` → 버튼으로 옮겨가도 `:focus-within`은 계속 true라서 상한이 흔들리지 않으니까요.

대신 **엉뚱한 곳이 망가졌습니다.**

![2안-운영방침](/image/키보드감지-2안-운영방침.gif)

리뷰 운영방침 안내 다이얼로그입니다. 입력 요소가 하나도 없는데 위아래 여백이 사라졌습니다.

범인은 **포커스 트랩**이었습니다. Radix는 다이얼로그를 열 때 접근성을 위해 내부 첫 요소에 포커스를 줍니다. 그러니 안내 팝업도 **열리는 순간 `:focus-within`이 true**가 되어버립니다.

```
inner=529   maxH=529.5px   dialog h=511 top=9 bottom=520
gapTop=9  gapBottom=9      ← 여백이 50px가 아니라 9px
focusWithin=true  active=BUTTON(확인)
```

| 기기 | 여백 (정상) | 여백 (2안) |
|---|---|---|
| 안드로이드 360×640dp | 50px | **9px** |
| iPhone SE 375×667pt | 50px | **43px** |

이 다이얼로그는 컨텐츠가 511px로 기본 상한(429px)을 넘기기 때문에, 상한이 풀리면 그 차이가 그대로 화면에 드러납니다.

사실 처음엔 "조건이 좀 느슨해도 컨텐츠가 상한보다 작으면 무해하지 않나?"라고 생각했었는데요. 리뷰 작성 다이얼로그의 컨텐츠(379px)만 보고 내린 결론이었습니다.

공용 `Dialog`는 컨텐츠가 더 긴 다이얼로그도 쓰기 때문에 그 전제가 성립하지 않더라구요. 공용 컴포넌트를 건드릴 땐 그 컴포넌트를 쓰는 모든 화면을 봐야 한다는 걸 다시 확인한 셈입니다.

## 3안. `:has(textarea):focus-within` — 채택

1안은 조건이 너무 타이트해서 저크가 났고, 2안은 너무 느슨해서 남의 다이얼로그를 건드렸습니다.

두 문제를 다시 보니 서로 다른 걸 묻고 있었습니다.

| | 셀렉터 | 성격 | 묻는 것 |
|---|---|---|---|
| `has-[textarea]` | `:has(textarea)` | **구조** (정적) | 이 다이얼로그가 텍스트 입력을 가지고 있나? |
| `focus-within` | `:focus-within` | **상태** (동적) | 지금 내부 어딘가에 포커스가 있나? |

**"입력을 가진 다이얼로그"라는 구조 조건**과 **"지금 포커스가 살아있다"는 상태 조건**을 AND로 묶으면 됩니다.

```tsx
// src/_common/components/dialog/dialog-components.tsx (DialogContent)
className={cn(
  'w-[calc(100vw-20px)] max-w-[320px] pt-8 bg-elevated-02 flex flex-col',
  // 기본: 디바이스 위아래 50px 여백을 남기고, 넘치는 내용은 본문에서 스크롤합니다.
  'max-h-[calc(100vh-100px)] supports-[height:100dvh]:max-h-[calc(100dvh-100px)]',
  // 텍스트 입력이 있는 다이얼로그에 한해, 내부에 포커스가 있으면(= 가상키보드 노출)
  // 여백을 없애고 가시 영역을 꽉 채웁니다.
  'has-[textarea]:focus-within:max-h-[100vh] has-[input]:focus-within:max-h-[100vh]',
  'supports-[height:100dvh]:has-[textarea]:focus-within:max-h-[100dvh]',
  'supports-[height:100dvh]:has-[input]:focus-within:max-h-[100dvh]',
  className,
)}
```

생성되는 셀렉터는 `.클래스:has(textarea):focus-within` 입니다. 케이스별로 따져보면 이렇습니다.

| 다이얼로그 / 상태 | `:has(textarea)` | `:focus-within` | 결과 |
|---|---|---|---|
| 리뷰 작성 — textarea 포커스 | ✅ | ✅ | `100dvh` |
| 리뷰 작성 — **별점 버튼** 포커스 | ✅ | ✅ | `100dvh` (저크 없음) |
| 리뷰 운영방침 — 확인 버튼 포커스 | ❌ | ✅ | 기본 상한 (여백 50px) |
| 포커스 없음 | – | ❌ | 기본 상한 |

별점을 탭해도 `:has(textarea)`는 여전히 참이니 상한이 유지되고, 안내 다이얼로그는 애초에 `textarea`가 없으니 포커스 트랩이 걸려도 조건에 걸리지 않습니다.

![3안-리뷰작성](/image/키보드감지-3안-리뷰작성.gif)

1안에서 저크가 났던 별점 탭 구간을 다시 재보니, 축소 구간이 사라지고 **단조 증가**만 남았습니다.

```
t=80249  inner=254  maxH=254.5px  h=255   TEXTAREA → BUTTON
t=80346  inner=324  maxH=254.5px  h=255   ← 상한 유지
t=80490  inner=529  maxH=254.5px  h=255
t=80562  inner=529  maxH=383.8px  h=379   ← 255 → 379 단조 증가
```

안내 다이얼로그의 여백도 정확히 돌아왔습니다.

![3안-운영방침](/image/키보드감지-3안-운영방침.gif)

```
안드로이드  maxH=429.5px  h=430  gapTop=50  gapBottom=50   focusWithin=true  hasTextarea=false
iPhone SE   maxH=497px    h=497  gapTop=50  gapBottom=50
```

덤으로 브라우저 지원 측면에서도 낫습니다. 조건의 동적인 부분을 `:focus-within`(Chrome 60+)이 담당하고 `:has()`는 정적 구조 판정만 하기 때문에, 셀렉터의 의미도 훨씬 명확해졌어요.

# 수정 후 검증

안드로이드(360×640dp)와 iOS(402×874pt)에서 상태별로 다시 계측했습니다.

| 기기 / 상태 | `max-height` | 다이얼로그 | 스크롤 | `등록` 버튼 |
|---|---|---|---|---|
| AOS — 키보드 노출 (뷰포트 254) | **254.5px** | h255 | h134 / sH258 → **가능** | **보임** |
| AOS — 키보드 닫힘 (포커스 유지) | 529.5px | h379 (컨텐츠 크기) | 불필요 | 보임 |
| AOS — 키보드 닫힘 (포커스 해제) | **429.5px** | h379 (컨텐츠 크기) | 불필요 | 보임 |
| iOS — 키보드 노출 (뷰포트 359) | **359px** | h359 | h238 / sH257 → **가능** | **보임** |
| iOS — 키보드 닫힘 (뷰포트 762) | **662px** | h378 (컨텐츠 크기) | 불필요 | 보임 |

세 가지 요구사항 모두 충족했습니다.

| 요구사항 | 결과 | 근거 |
|---|---|---|
| 1. 컨텐츠만큼 높이 | ✅ | 상한(429.5 / 662)보다 컨텐츠(379 / 378)가 작아 그대로 렌더 |
| 2. 여백 50px + 스크롤 | ✅ | 포커스 해제 시 상한이 `100dvh - 100px`로 계산됨 |
| 3. 키보드 시 꽉 채움 | ✅ | 상한이 `100dvh`로 전환되어 가시 영역을 정확히 채움 (254 / 359) |

## 포커스는 있는데 키보드는 없는 경우

`:focus-within`은 어디까지나 키보드의 **프록시**입니다. 그러니 둘이 어긋나는 상태가 존재합니다.

| 상황 | 발생 |
|---|---|
| 안드로이드 백키·⌄ 버튼으로 키보드만 내림 | textarea 포커스 유지 |
| 하드웨어 키보드 연결 (블루투스·태블릿 키보드 케이스) | 소프트 키보드 미노출 |
| PC 웹 | 항상 |

이 상태에서 상한은 `100dvh`로 남습니다. 여백 50px 규칙이 잠시 풀린 상태인 셈이죠.

그런데 **결과적으로는 무해합니다.** `max-height`는 상한일 뿐이고 실제 높이는 컨텐츠가 결정하니까요. 실측해보면 포커스 유지 + 키보드 닫힘 상태에서 상한은 529.5px지만 다이얼로그는 컨텐츠 크기인 **379px 그대로**입니다.

영향이 생기려면 `컨텐츠 > 뷰포트 − 100px`, 즉 키보드 없이 뷰포트가 478px 미만이어야 하는데, 세로 화면에서는 안드로이드 529 / SE 597 / 17 Pro 762라 해당 사항이 없었습니다.

안드로이드 백키로 키보드만 내리는 경로도 확인해봤는데, 포커스가 유지되니 상한이 `100dvh`로 남고 뷰포트가 커지는 만큼 **단조 증가만** 합니다(255 → 280 → 379). 저크 없이 자연스럽게 복귀합니다.

## 브라우저 호환성

| 기능 | 최소 Chrome | 실패 시 |
|---|---|---|
| `max-h-[calc(100vh-100px)]` | 19+ | — |
| `@supports (height:100dvh)` | 28+ | 조건 false → `vh` 폴백 (리사이즈 모드에선 `vh` == `dvh`라 손실 없음) |
| `dvh` 단위 | 108+ | 위 `@supports`가 차단 |
| `:focus-within` | 60+ | — |
| **`:has()`** | **105+** | 요구사항 3만 미적용. 요구사항 1·2는 정상 동작 |

`:has()`를 지원하지 않는 구형 브라우저에서는 요구사항 3만 빠지고 나머지는 그대로 동작합니다. 안전하게 폴백되는 구조입니다.

참고로 생성된 CSS를 뜯어보니 프로젝트는 이미 Chrome 111+를 요구하고 있었습니다. `color-mix()` 25회, `oklch()` 1회, `:has()`는 이번 변경 이전부터 27회 쓰이고 있더군요. Tailwind v4의 공식 지원 하한선도 Chrome 111 / Safari 16.4 입니다.

# 추가로 알게 된 점 — resizeToAvoidBottomInset은 iOS에서도 동작합니다

사내에서는 "리사이즈/오버레이 선택은 안드로이드만 가능하고, iOS는 무조건 리사이즈"로 알려져 있었습니다. 관련 훅에도 그렇게 주석이 달려 있었고요.

그런데 **사실이 아니었습니다.**

플러터 쪽에서 플래그만 바꿔 iOS를 재빌드해 비교해보니 이렇게 나왔습니다.

| | `resizeToAvoidBottomInset: true` | `false` |
|---|---|---|
| `innerHeight` | 762 → **359** (줄어듦) | 762 → **762** (유지) |
| `visualViewport` | 762 → 359 | 762 → **359** |
| `DIFF` | **0** | **403** |
| 판정 | 리사이즈 | **오버레이** |

`resizeToAvoidBottomInset`은 플랫폼 코드가 아니라 **플러터 `Scaffold` 프레임워크 속성**입니다. `MediaQuery.viewInsets.bottom`을 body 높이에서 뺄지 결정할 뿐이고, iOS도 `FlutterViewController`가 키보드 노티피케이션으로 이 값을 채워줍니다.

안드로이드 전용인 건 그 아래층의 `windowSoftInputMode`(`adjustResize` / `adjustPan`)뿐이었습니다.

CSS 몇 줄로 끝난 수정이지만, 그 몇 줄을 고르기까지의 과정이 더 기억에 남습니다.

이번 작업에서 얻은 것들을 정리하면 이렇습니다.

| 구분 | 내용 |
|---|---|
| **올바른 규칙도 맥락이 바뀌면 버그가 된다** | "위아래 50px 여백"은 잘못된 규칙이 아니었습니다. 다만 뷰포트가 절반으로 줄어드는 상황을 전제하지 않았을 뿐이죠. |
| **공용 컴포넌트는 모든 사용처를 봐야 한다** | 2안이 통과할 뻔했던 건 리뷰 작성 다이얼로그 하나만 봤기 때문입니다. |
| **프록시 조건은 어긋나는 구간을 반드시 확인** | 포커스는 키보드가 아닙니다. 어긋나는 순간(별점 탭, 백키)을 실측하지 않았다면 저크를 못 잡았을 겁니다. |
| **"알려진 사실"도 한 번은 재봐야 한다** | iOS는 무조건 리사이즈라는 통념이 틀렸습니다. 플래그만 바꿔 재빌드해보니 iOS도 그대로 오버레이로 동작하더군요. |

특히 세 번째가 컸는데요. 처음엔 1안으로 PR을 올릴 뻔했습니다. 기능적으로는 아무 문제가 없었으니까요. 실기기에서 손으로 직접 만져보지 않았다면 저크는 그대로 나갔을 겁니다.

## 남은 고민

`:focus-within`을 키보드의 프록시로 쓰는 건 어디까지나 **우회**입니다. 리사이즈 모드라는 전제가 깨지면(앱이 특정 화면을 오버레이로 바꾸면) 이 CSS는 조용히 잘못된 값을 계산하게 됩니다.

근본적으로는 앱이 **"지금 이 웹뷰가 리사이즈인지 오버레이인지"** 를 웹에 알려주는 게 맞다고 생각합니다. 화면 단위로 두 모드가 섞여 있는 이상, 웹이 그걸 추측하는 방식은 언젠가 또 어긋날 테니까요.
