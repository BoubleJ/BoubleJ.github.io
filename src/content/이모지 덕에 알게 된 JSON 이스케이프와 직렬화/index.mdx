사내 서비스에서 응답값을 해싱해 검증하는 로직이 있는데 이모지가 섞인 응답에서만 검증이 깨진 일이 있었습니다.

원인을 쫓다 보니 axios의 기본 동작부터 raw 텍스트와 JSON 파싱까지 하나씩 들여다보게 됐는데요.

이 글은 그 과정에서 정리한 내용입니다.

# 문제가 된 코드

제가 겪은 이슈를 먼저 간략히 설명드리자면

프론트는 백엔드 API의 응답을 받으면 응답 객체를 문자열로 치환한 뒤 HMAC 검증에 사용합니다. 백엔드도 마찬가지로 응답을 내려보내기 전에 같은 방식으로 문자열로 치환해 HMAC 값을 만들어줍니다.

즉 양쪽이 만든 값이 같아야 이 응답은 중간에 조작되지 않았다고 판단하도록 설계되어 있습니다.

사내 Next 서비스는 HTTP 인터페이스로 axios를 사용하고 있는데요. 응답값을 해싱하기 전에 문자열로 치환하는 로직이 아래와 같이 세팅되어 있었습니다.

```ts
const resString = typeof res.data === 'string' ? res.data : JSON.stringify(res.data)
```

응답이 꼭 객체라는 보장이 없기 때문에 문자열이면 그대로 쓰고 객체 형태면 `JSON.stringify`로 직렬화한 뒤 해싱하는 것이죠.

평소에는 문제가 없었는데 응답값에 이모지가 섞여 내려올 경우 문제가 발생했습니다.

# 백엔드 응답을 직렬화하기까지의 흐름

 백엔드에서 내려온 응답은 크게 세 단계를 거쳐갑니다. 각 단계에서 문자열이 어떻게 바뀌는지 따라가 보겠습니다.

## 1. 백엔드는 이모지를 escape해서 내려준다

백엔드는 Jackson 직렬화를 거치면서 이모지를 `\ud83c\udf89` 형태로 escape해서 내려보냅니다.

한글도 이모지도 모두 비ASCII 문자인데 Jackson은 둘을 다르게 내보냅니다. 한글은 글자 그대로 나가고 이모지만 escape됩니다. 

### 왜 이모지만 escape될까

용어부터 정리하고 가겠습니다.

- **ASCII 문자 :**영문자와 숫자와 기본 기호입니다. `A` `7` `{` 처럼 컴퓨터가 초기부터 다루던 128개 문자를 말합니다.
- **비ASCII 문자 :**그 밖의 모든 문자입니다. 한글과 이모지와 한자 등이 포합됩니다.
- `\uXXXX` **이스케이프**: 문자를 적는 방식입니다. 글자를 그대로 쓰는 대신 그 문자에 매겨진 번호를 16진수 네 자리로 적습니다. 예를 들어 한글 '안'을 `\uc548` 로 쓰는 식이죠. 어떤 문자든 이 방식으로 적을 수 있고 JSON 규격상 두 표기 다 유효합니다.

여기서 중요한 건 `\uXXXX` 가 **16비트 값 하나를 적는 표기**라는 점입니다. 16진수 네 자리로 담을 수 있는 범위가 정해져 있다는 뜻이죠.

한글은 이 범위 안에 들어갑니다. 예를 들어`안` 은 `\uc548`입니다.

반면 이모지는 들어가지 않습니다. 🎉 는 16비트로 담을 수 없는 번호라서 `\ud83c` 와 `\udf89` 두 값을 짝지어 하나의 문자를 나타냅니다. 이것을 **서로게이트 쌍**이라고 부릅니다.

Jackson은 이렇게 쪼개지는 문자만 escape하고 나머지는 글자 그대로 내보냅니다. 

## 2. axios는 응답값을 먼저 파싱 후 인터셉터로 넘어간다

그렇다면 프론트에서도 escape 시퀀스를 그대로 받아야 할 텐데 확인해보니 이미 literal 🎉 이모지 형태로 도착하더군요.

즉 프론트에 도착한 시점에는 이미 literal 이모지라서 백엔드가 내보낸 escape 형태를 되살릴 수 없었던 겁니다.

<br />

분명 백엔드에서는 이스케이프 처리해서 내려줬는데 왜 프론트는 리터럴 형태로 받은걸까요?

원인은 axios의 기본 동작에 있었습니다. axios는 응답을 받으면 `transformResponse`를 먼저 실행하고 그 다음에 인터셉터를 실행합니다. `JSON.parse`가 이 `transformResponse` 안에서 일어나기 때문에 인터셉터가 열릴 때는 이미 raw 텍스트가 사라진 뒤입니다.



## 3. JSON.stringify는 다시 escape하지 않는다

그렇다면 `JSON.stringify`로 되돌릴 때 다시 escape되지 않을까요?

확인해보니 🎉 이모지는 `JSON.stringify`를 거쳐도 literal 이모지 문자 그대로 출력됐습니다.

왜 그런지 두 함수가 하는 일부터 짚어보겠습니다.

### JSON.parse와 JSON.stringify가 하는 일

- **JSON.parse** : JSON 텍스트를 읽어 자바스크립트 값으로 만듭니다. `{"t":"안녕"}` 이라는 문자열이 `{ t: '안녕' }` 객체가 되죠.
- **JSON.stringify** : 반대로 자바스크립트 값을 JSON 텍스트로 출력합니다. `{ t: '안녕' }` 객체가 `{"t":"안녕"}` 문자열이 됩니다.

여기서 놓치기 쉬운 점이 있습니다. 두 함수는 **텍스트와 값 사이를 오가는 변환**이지 원본 텍스트를 보관해두는 장치가 아닙니다. 그래서 `JSON.parse` 했다 다시 `JSON.stringify` 처리해도 기존값과 동일하다는 보장이 없습니다.

```ts
const literal = '{"t":"🎉"}'
const escaped = '{"t":"\\ud83c\\udf89"}'

JSON.parse(literal)   // { t: '🎉' }
JSON.parse(escaped)   // { t: '🎉' }    두 값은 완전히 같습니다

JSON.stringify(JSON.parse(literal))   // '{"t":"🎉"}'    literal 과 동일
JSON.stringify(JSON.parse(escaped))   // '{"t":"🎉"}'    escaped 와 다름
```

`JSON.stringify`는 어떤 값을 받든 **literal로 출력합니다.** 그래서 두 경우 모두 결과가 `{"t":"🎉"}` 하나로 나옵니다.

원본이 literal이었다면 이 결과와 애초에 같은 형태였으니 기존값과 동일합니다.

원본이 escape였다면 이야기가 다릅니다. `JSON.parse`가 값만 남기고 표기법을 버리기 때문에 원래 escape로 적혀 있었다는 사실을 알 방법이 없어요. 그래서 `JSON.stringify`도 그 표기를 되살리지 못하고 literal로 출력해버립니다.

정리하면 기존값과 동일한 경우는 원본이 `JSON.stringify`가 출력하는 형태와 처음부터 같았을 때뿐입니다.

두 문자열은 JSON으로 읽으면 같은 값입니다. 그런데 문자열로 비교하면 다릅니다.

```ts
import { isDeepStrictEqual } from 'node:util'

literal === escaped                                          // false   문자열로 비교
isDeepStrictEqual(JSON.parse(literal), JSON.parse(escaped))  // true    값으로 비교
```

`isDeepStrictEqual`은 Node가 제공하는 깊은 비교 함수입니다. 두 값이 같다고 나오는데도 문자열 비교는 어긋나는 것이죠.

### JSON.parse는 표기법 정보를 남기지 않는다

`"\ud83c\udf89"` 와 `"🎉"` 는 적는 방식만 다를 뿐 JSON에서는 **같은 값을 가리킵니다.**

파싱이 끝나고 나면 메모리에는 문자열 값만 남습니다. "원래 escape로 적혀 있었다"는 정보는 이 시점에 사라져요. 되살리고 싶어도 되살릴 정보 자체가 없는 겁니다.

### JSON.stringify는 스펙이 정한 것만 escape한다

그럼 `JSON.stringify`가 알아서 escape해주면 되지 않을까 싶지만 그렇게 동작하지 않습니다. ECMA-262가 정한 escape 대상은 다음뿐입니다.

- 큰따옴표 `"`
- 역슬래시 `\`
- 제어 문자(U+0000 – U+001F)
- 짝 잃은 lone surrogate (ES2019+)

비ASCII 문자를 JSON 텍스트에 literal로 넣는 것은 규격에 어긋나지 않습니다. 그래서 한글이든 이모지든 그대로 출력합니다. Jackson의 `ESCAPE_NON_ASCII` 같은 "비ASCII를 escape하라"는 옵션이 `JSON.stringify`에는 아예 존재하지 않아요.

### 그래서 literal 표기로 정규화된다

`JSON.parse`가 표기법 정보를 지우고 `JSON.stringify`가 literal로 출력합니다. 그래서 escape 표기 → parse → stringify를 거치면 **literal 표기로 정규화**됩니다.

즉 백엔드가 내려보낸 문자열과 프론트가 해싱하는 문자열이 서로 달랐던 것입니다. 해싱하기로 약속한 형태는 escape 시퀀스인데 literal 이모지를 해싱하고 있었으니 검증이 통과할 수 없었죠.

# 해결

axios의 자동 파싱을 끄고 raw 텍스트로 검증한 뒤 직접 파싱하도록 바꿨습니다.

```ts
{
  responseType: 'text',
  transformResponse: [],
}
```

`responseType: 'text'`는 응답을 어떤 타입으로 받을지 정합니다. 기본값은 `json`이라 axios가 응답 본문을 객체로 만들어 넘기는데 `text`로 두면 문자열 그대로 들고 옵니다.

`transformResponse: []`는 응답 변환 파이프라인을 비웁니다. axios의 기본 `transformResponse`는 문자열을 받으면 `JSON.parse`를 시도하는데 배열을 비워두면 그 단계가 사라집니다.

```ts
// 기본 설정
res.data   // { t: '🎉' }            파싱된 객체

// 위 설정을 준 뒤
res.data   // {"t":"\ud83c\udf89"}   백엔드가 보낸 텍스트 그대로
```

백엔드가 escape로 적어 보낸 형태가 그대로 남습니다. 이 문자열을 그대로 해싱하면 백엔드가 해싱한 문자열과 같으니 검증이 통과됩니다. `JSON.stringify`를 거치지 않으니 literal로 바뀔 일도 없고요.

검증을 마친 뒤에 직접 `JSON.parse`를 호출해 객체로 만들어 쓰면 됩니다.

axios에서 제공하는 편의성을 이용하지 못하는 건 아쉬웠지만 근본적으로 raw 텍스트에서부터 해싱 처리를 해야 했기 때문에 뾰족한 수가 없었습니다.

## raw 텍스트가 뭐길래

`res.data`가 객체로 도착하다 보니 응답이 원래부터 객체라고 생각하기 쉬운데요. 네트워크를 타고 오는 것은 객체가 아니라 **문자열**입니다.

서버는 자기가 가진 객체를 규칙에 맞는 텍스트로 적어서 보내고 클라이언트는 받은 텍스트 자체를 사용할 일이 없으니 다시 객체로 만듭니다.

raw 텍스트는 **아무런 가공처리 안 된 상태** 그대로를 의미합니다. 백엔드가 이모지를 escape해서 적었다면 raw에는 escape가 그대로 들어 있습니다. 해석하기 전이니 백엔드가 적은 그대로인 것이죠.

해싱해야 할 대상이 바로 이겁니다. 백엔드도 자기가 내보내는 텍스트로 해시를 만들었으니 프론트도 같은 텍스트를 써야 값이 일치합니다.

# 정리

1. **JSON은 같은 값이어도 표현하는 문자열이 여러 가지일 수 있습니다.**  
escape 표기부터 공백과 숫자 표기와 키 순서까지 모두 자유롭습니다. 두 JSON이 의미상 같아도 문자열로는 다를 수 있습니다.
2. **JSON.parse 했다 다시 JSON.stringify 해도 기존값이 돌아오지 않습니다.**  
파싱하는 순간 표기법 정보가 사라지고 `JSON.stringify`는 스펙에서 정해진 영역만 escape하기 때문입니다.

# 만약 fetch를 사용했다면 어땠을까?

그렇다면 만약 fetch를 사용한다면 이러한 이슈를 어떻게 해결하면 될까요?

결론부터 말하면 **따로 설정할 것이 없습니다.** fetch는 응답을 `Response` 객체로 돌려주는데요. `Response` 객체로부터 raw 텍스트값을 추출할 수 있습니다.

```ts
const res = await fetch(url)

const raw = await res.text()   // 실제로 전송된 텍스트
verifyHmac(raw)                // raw 그대로 검증

const data = JSON.parse(raw)   // 검증을 마친 뒤 파싱
```

## Response 객체

> **Response 객체란?** <br /> fetch가 반환하는 응답 객체입니다. 상태코드와 헤더 그리고 본문을 함께 들고 있어요. 본문은 아직 읽히지 않은 상태로 들어 있습니다.

본문을 꺼내려면 메서드를 직접 호출해야 합니다.

- `res.text()` : 본문을 문자열로 읽습니다. 이게 raw 텍스트입니다.
- `res.json()` : 문자열로 읽은 뒤 `JSON.parse`까지 해서 객체로 돌려줍니다.

한 가지 제약이 있습니다. **본문은 한 번만 읽을 수 있어요.** `res.json()`을 부른 뒤에 `res.text()`로 원문을 다시 꺼내려 하면 에러가 납니다. 둘 다 필요하다면 `res.clone()`으로 사본을 만들어 각각 읽으면 됩니다.

# 궁금한 점

지금은 raw 텍스트를 해싱하는 방식으로 해결했지만 서버와 클라이언트가 각자 다른 언어와 라이브러리를 쓰는 상황에서 이 방식이 항상 최선인지는 아직 잘 모르겠습니다.

RFC 8785처럼 정규화(canonicalization)된 JSON을 해싱하는 접근이 더 나은 상황도 있을 텐데 [정규화 접근의 한계를 다룬 글](https://www.da.vidbuchanan.co.uk/blog/signing-json.html)도 있어서 두 접근의 트레이드오프를 좀 더 공부해봐야 할 것 같습니다.
