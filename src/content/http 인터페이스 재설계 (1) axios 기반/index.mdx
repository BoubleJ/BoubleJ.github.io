공통 인터페이스는 프로젝트 전역에서 쓰이기 때문에 잘 설계해야 합니다. 설계를 잘못하면 모든 사용처에서 쓰기 불편해지고 예상하지 못한 버그를 만나기도 하는데요. 요구사항이 바뀌었을 때 유연하게 대응하기도 어렵습니다.



이 글에서는 사용성이 좋지 않았던 기존 http 인터페이스를 재설계하는 과정에서 겪었던 고민과 트러블슈팅을 공유하고자 합니다.



# 기존 http 인터페이스의 문제



기존 http 인터페이스 사용 방식에는 두 가지 문제가 있었어요.

### 1. 매번 사용처에서 주입하는 필수헤더

저희 서비스는 디바이스 환경에 따라 노출할 수 있는 작품 목록이 다릅니다. 그래서 모든 api 요청에 채널헤더를 필수로 넘겨야 했는데요. 모든 요청에 같은 값을 넘기는 헤더라면 인터페이스 구현체 안에서 넣는 게 자연스럽겠죠. 그런데 기존 인터페이스는 이 헤더를 사용처에서 직접 넣어야 하는 방식이었습니다.

이렇게 되면 누군가 헤더를 넘기는 것을 잊었을 때 에러가 발생하는 문제점이 있습니다.

### 2. 메서드 체이닝 문제

api 를 호출하는 데 필요한 값은 보통 url 과 파라미터와 http 메서드 정도입니다. 그런데 기존 인터페이스는 단순한 api 를 호출할 때도 이 값들 외에 추가 메서드가 필요한 경우가 많았습니다. config 같은 추가 설정을 넘기는 것도 아닌데 말이죠.

```typescript
export async function getData(params: RankingsGenresParams) {
  const url = '...api'
  const res = await new Fetch(url)
    .addHeader(params.host)
    .addParams(deleteHostParam(params))
    .request<Res>()

  return res
}
```



심지어

```typescript
 const url = 'api...'
  const res = new Fetch(url, '')
    .httpMethod('POST')
    .addHeaderContent('xForm')
    .addParams(fetchParam)
    .addBodyNull(false)
    .request<Res>()
  return res
```

메서드가 5개나 붙는 경우도 있었습니다.

메서드가 많아질수록 사용하는 개발자는 입장에선 부담스러울 수 밖에 없습니다. 메서드마다 어떤 역할을 하는지 알아야 하기 때문이죠. 

메서드 호출 순서가 따로 정해져 있나? 이 메서드는 뭐지? 놓친 메서드는 없나? 하는 고뇌에 빠지게 됩니다.

잘 만든 공통 인터페이스는 내부 동작을 몰라도 쉽게 사용할 수 있어야 한다고 생각합니다. 그런데 기존 인터페이스는 그러지 못했죠. 실제로 팀원들도 불편하다는 이야기를 많이 했었어요.

# axios 로 새 인터페이스 만들기

이런 문제를 해결하려고 http 인터페이스를 새로 만들기로 했습니다. 먼저 http 라이브러리를 골라야 했는데요. 저는 axios 를 골랐습니다.

사실 이때만 해도 기술을 고를 때 깊이 고민하지 않았습니다. 누군가 왜 axios 를 골랐냐고 물었다면 "음... 인터셉터 기능이 좋아서요? 편해서요?" 라고 답했을 것 같아요. 틀린 이유는 아니지만 남들이 좋다고 하니까 쓰는 것에 가까웠죠.

axios 가 좋지 않은 라이브러리라는 뜻은 아닙니다. 다만 fetch, ky 등 axios 외 다양한 선택지가 있고 그중 저희 서비스 상황에 가장 맞는 라이브러리가 무엇인지 고민하지 않았다는게 돌이켜보면 아쉬운 부분 중 하나입니다.



## 목표

어찌됐든 axios 로 구현을 시작했습니다. 구현 목표는 세 가지로 잡았습니다.



### 1. 사용처 로직 최소화

- 사용처에서는 http 메서드와 api 엔드포인트와 파라미터만 넘긴다.
- config 는 옵셔널로 받아서 필요할 때만 넘긴다.
- 파라미터는 http 메서드와 관계없이 같은 형태의 객체로 넘긴다. 메서드에 맞게 쿼리스트링이나 body 로 바꾸는 작업은 구현체 안에서 한다.



### 2. 그 외 나머지 처리는 구현체 내부에서 처리

- 필수 헤더와 세션 쿠키 같은 헤더 값은 구현체 안에서 넣는다.
- 에러 핸들링과 요청과 응답 과정에서 처리해야 하는 비즈니스 로직도 구현체 안에서 처리한다.
- 사용하는 개발자는 구현체 내부 로직을 몰라도 쓰는 데 지장이 없어야 한다.



### 3. 라이브러리 교체 시 구현체만 갈아끼워도 되도록 추상화

- 요구사항은 언제든 바뀔 수 있고 지금 쓰는 라이브러리가 나중에는 맞지 않을 수도 있다. 그래서 라이브러리를 바꾸더라도 구현체만 수정하면 되도록 설계한다.
- 사용처 코드는 바꾸지 않거나 바꾸더라도 최소한으로 줄인다.

## 공통 로직만 포함된 base 클래스

```typescript

export function createAxiosInstance(baseUrl: string | undefined, timeout: number, config: AxiosRequestConfig) {
  const axiosInstance = axios.create({
    baseURL: baseUrl,
    timeout,
    paramsSerializer: (params) => {
      return qs.stringify(params, { arrayFormat: 'comma' })
    },
    ...config,
  })
  return axiosInstance
}

export abstract class BaseAxios implements ApiInterface {
  protected instance: AxiosInstance

  constructor({
    baseUrl,
    timeout,
    config,
  }: {
    baseUrl: string | undefined
    timeout: number
    config: AxiosRequestConfig
  }) {
    this.instance = createAxiosInstance(baseUrl, timeout, config)
    this.setInterceptors()
  }

  protected abstract setInterceptors(): void

  public get<R = unknown>(url: string, { params, config }: ApiOptions = {}) {
    return this.instance.get<R>(url, {
      params,
      headers: config,
    })
  }

  public post<R = unknown>(url: string, { params, config }: ApiOptions = {}) {
    return this.instance.post<R>(url, params, {
      headers: config,
    })
  }

  public put<R = unknown>(url: string, { params, config }: ApiOptions = {}) {
    return this.instance.put<R>(url, params, {
      headers: config,
    })
  }

  public patch<R = unknown>(url: string, { params, config }: ApiOptions = {}) {
    return this.instance.patch<R>(url, params, {
      headers: config,
    })
  }

  public delete<R = unknown>(url: string, { params, config }: ApiOptions = {}) {
    return this.instance.delete<R>(url, {
      data: params,
      headers: config,
    })
  }
}
```



`createAxiosInstance` 는 모든 요청에 똑같이 들어가는 설정을 포함해 axios 인스턴스를 만듭니다. 

`paramsSerializer` 에 qs 의 `arrayFormat: 'comma'` 를 지정해서 혹시나 사용처에서 파라미터를 배열 형태로 넘길 경우 `ids=1,2,3` 형태의 쿼리스트링으로 보내기 위함입니다.

`BaseAxios` 는 생성자에서 인스턴스를 만들고 바로 `setInterceptors` 를 호출합니다. `setInterceptors` 는 abstract 메서드로 설정해 상속받는 클래스가 반드시 구현하도록 만들었습니다. 아래에 나오는 서버용과 클라이언트용 클래스가 이 메서드에서 각자 인터셉터를 등록합니다.

http 메서드 특성상 메서드마다 파라미터를 넣는 방식이 다른데요. `get` 은 `params` 를 쿼리스트링으로 보내고 `post` `put` `patch` 는 두 번째 인자인 body 로 보내고 `delete` 는 `data` 옵션에 담아 보냅니다. 

이 차이점을 사용처에서 매번 구분하긴 번거로운 작업입니다. 때문에 `BaseAxios` 안에서 해결하도록 위임하고  다섯 메서드 모두 사용처에서 `(url, { params, config })` 형태로 인자를 받도록 설계했습니다. 이렇게 해서 앞서 세운 첫 번째 목표인 "사용처 로직 최소화" 를 달성했습니다. 사용처는 http 메서드와 url 과 파라미터만 넘기면 돼요.



그리고 `BaseAxios` 는 `ApiInterface` 를 implements 하고 있는데요. `ApiInterface` 는 http 메서드들의 이름과 인자 형태를 정의한 인터페이스입니다.

```typescript
export interface ApiOptions {
  params?: object
  config?: RequestHeader
}

interface ApiInterface {
  get<R = unknown>(url: string, options?: ApiOptions): Promise<AxiosResponse<R>>
  post<R = unknown>(url: string, options?: ApiOptions): Promise<AxiosResponse<R>>
  put<R = unknown>(url: string, options?: ApiOptions): Promise<AxiosResponse<R>>
  delete<R = unknown>(url: string, options?: ApiOptions): Promise<AxiosResponse<R>>
  patch<R = unknown>(url: string, options?: ApiOptions): Promise<AxiosResponse<R>>
}
```

사실 `implements ApiInterface` 를 빼도 동작에는 문제가 없습니다. 그래도 붙여둔 이유는 메서드 이름과 인자 형태를 타입 레벨에서 강제하기 위해서인데요. `implements` 를 붙이면 클래스가 인터페이스의 메서드를 빠짐없이 같은 형태로 구현했는지 컴파일할 때 검사합니다. 나중에 다른 http 라이브러리로 구현체를 새로 만들더라도 사용처가 쓰는 `(url, { params, config })` 형태를 유지 시키기 위함이죠



이러면 상술했던 1번째 목표를 달성하게 됩니다. 사용처는 url, http메서드, 파라미터만 넘기도록 된거죠



## 헤더 주입

```typescript

export default class ApiServer extends BaseAxios {
  protected setInterceptors() {
    setServerInterceptors(this.instance)
  }
}

const setServerInterceptors = (instance: AxiosInstance) => {
  instance.interceptors.request.use((config) => {
    return onRequest(config, {
    [HEADER.CHANNEL]: getChannelServer(),
    [HEADER.COOKIE]: getCookieServer(),
    })
  })
  instance.interceptors.response.use(onResponse, onErrorResponse)
}


```

`ApiServer` 는 `BaseAxios` 를 상속받고 `setInterceptors` 에서 `setServerInterceptors` 를 호출합니다. 서버 컴포넌트에서 api 를 요청할 때 이 클래스를 써요.

요청 인터셉터는 채널헤더와 쿠키(세션 쿠키)를 `onRequest` 에 넘겨서 api 요청에 붙이도록 했습니다. 이렇게하면 채널헤더를 사용처에서 직접 넘기지 않아도 되죠.

`getChannelServer()` 와 `getCookieServer()` 는 Next.js 의 `headers()` 와 `cookies()` 로 브라우저가 보낸 요청을 읽습니다.

즉 `getChannelServer()` 는 채널헤더 값을 읽고 `getCookieServer()` 는 쿠키를 읽어서 api 요청에 넘기는거죠.

쿠키를 직접 넣는 이유는 Next.js 서버에서 보내는 요청에는 쿠키가 자동으로 실리지 않기 때문인데요. 

사용자가 서비스에 접근하면 요청은 브라우저 → Next.js 서버 → 백엔드 api 순서로 전달됩니다. 

브라우저가 Next.js 서버로 보낸 요청에는 쿠키가 실립니다. 하지만 Next.js 서버가 백엔드로 다시 보내는 요청은 서버 간 요청이라서 브라우저 쿠키가 자동으로 붙지 않습니다. 그래서 브라우저 요청에 실려 온 쿠키를 읽어 백엔드 요청 헤더에 직접 넣어줬습니다.



```typescript

export default class ApiClient extends BaseAxios {
  protected setInterceptors() {
    setClientInterceptors(this.instance)
  }
}

export const setClientInterceptors = (instance: AxiosInstance) => {
  instance.interceptors.request.use((config) =>
    onRequest(config, {
      [HEADER.CHANNEL]: getChannelForClient(),
    }),
  )
  instance.interceptors.response.use(onResponse, onErrorResponse)
}

```

`ApiClient` 도 `BaseAxios` 를 상속받고 `setInterceptors` 에서 `setClientInterceptors` 를 호출합니다. 클라이언트 컴포넌트에서 api 를 요청할 때 이 클래스를 써요.

채널헤더 값은 `getChannelForClient()` 가 쿠키에서 읽어옵니다. 이때 쿠키는 next와 달리  브라우저에서는 document.cookie 로 쿠키 문자열을 읽고 파싱해서 값을 꺼내옵니다. 브라우저 환경에서 동작하는 로직이기 때문이죠.



## 서버용과 클라이언트용 클래스를 나눈 이유

여기서 궁금한 점이 생길 수 있습니다. 

> 필수헤더값을 왜 클라이언트용 서버용으로 나누었나요??

위 코드에서 보듯이 Next.js 서버에서 헤더를 주입하는 방식과 클라이언트에서 헤더를 주입하는 방식이 다른데요.



사실 저도 인터페이스를 만들면서 클라이언트와 서버가 같은 인터페이스를 쓰고 헤더도 구현체 안에서 주입하도록 설계해 봤는데요.

결론부터 말씀드리면 Next.js 의 특성상 어렵다고 판단했습니다.



&nbsp;

### 1. typeof window 로 서버와 클라이언트 분기하기

`typeof window === 'undefined'` 조건으로 실행 환경을 나눠서 헤더를 넣는 방법을 먼저 시도해봤어요.

```typescript

//interceptors.ts

const getHeader = () => {
  if (typeof window === 'undefined') {
    return getRequestHeader()
  }
  return getClientRequestHeader()
}
```

하지만 이 방법에는 근본적인 문제가 있었습니다. 파일에서 import 한 모듈은 `typeof window === 'undefined'` 조건이 성립하는지와 관계없이 번들에 들어가는데요. 이 파일(`interceptors.ts`)은 서버용 헤더 함수에 필요한 `next/headers` 와 클라이언트용 헤더 함수를 모두 import 하고 있습니다. 그래서 Client Component 에서 이 파일을 import 하면 `next/headers` 도 함께 들어갑니다. `next/headers` 는 서버 컴포넌트에서만 쓸 수 있는 모듈이라서 Next.js 는 빌드할 때 아래 에러를 던집니다.

```
You're importing a component that needs next/headers. That only works in a Server Component but one of its parents is marked with "use client", so it's a Client Component.

 1 | import type { AxiosInstance } from 'axios'
 2 | import { headers } from 'next/headers'
   : ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Import trace for requested module:
./interceptors.ts
./axiosClient.ts
```



&nbsp;

&nbsp;

### 2. lazy import 로 모듈을 불러오는 시점 늦추기

그렇다면 lazy import 로 모듈을 불러오는 시점을 늦추면 되지 않을까요? 코드가 실행될 때 서버에서는 서버용 모듈만 불러오고 클라이언트에서는 클라이언트용 모듈만 불러오도록 바꿔봤습니다.

```typescript
const getHeader = async () => {
  if (typeof window === 'undefined') {
    const { getRequestHeader } = await import('./serverHeader')
    return getRequestHeader()
  }
  const { getClientRequestHeader } = await import('./clientHeader')
  return getClientRequestHeader()
}
```

그런데 Client Component 는 브라우저에서만 실행되지 않습니다. 사용자가 페이지에 처음 들어오면 Next.js 는 서버에서 HTML 을 미리 만드는데요. 이때 Client Component 도 서버에서 한 번 실행됩니다. 서버에는 `window` 가 없어서 `typeof window === 'undefined'` 조건이 성립하고 `import('./serverHeader')` 분기를 타게 됩니다. 문제는 서버에서 실행되더라도 Next.js 가 이 코드를 Client Component 의 코드로 본다는 점이에요. 그래서 `serverHeader.ts` 가 import 한 `next/headers` 때문에 1번과 같은 에러가 납니다.

```
You're importing a component that needs next/headers. That only works in a Server Component but one of its parents is marked with "use client", so it's a Client Component.

 1 | import { headers } from 'next/headers'
   : ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Import trace for requested module:
./serverHeader.ts
./interceptors.ts
./axiosClient.ts
```

결국 lazy import 는 모듈을 실행하는 시점만 늦출 뿐 Client Component 의 코드에 `next/headers` 가 들어가는 것은 막지 못했어요.

### 3. webpack 설정 바꾸기

그렇다면 webpack 설정을 바꿔서 서버와 클라이언트에서 서로 다른 파일을 불러오게 하면 어떨까요? `next.config.js` 의 `webpack` 설정에서 `resolve.alias` 를 쓰면 같은 import 경로가 환경마다 다른 파일을 가리키도록 만들 수 있긴합니다.

하지만 이 방법도 마냥 순탄하진 않습니다. `webpack` 설정 함수가 받는 `isServer` 는 서버 번들인지 클라이언트 번들인지만 알려줍니다. 2번에서 본 Client Component 를 서버에서 렌더링하는 번들도 서버 번들에 속하는데요. 그래서 `isServer` 로 나누면 이 번들에 서버용 파일이 들어가고 1번과 같은 에러가 납니다. 이 번들까지 구분하려면 Next.js 가 내부에서 번들을 나누는 방식까지 다뤄야 합니다.

이렇다보니 헤더를 넣는 위치 하나를 합치려고 이렇게 빌드 설정까지 바꾸는 게 맞는지 의문이 들었어요.



&nbsp;

&nbsp;

### 4. 트레이드오프

지금 구조를 보면 서버와 클라이언트는 api 를 요청 시 동일한 채널헤더 값을 넘기지만 각 체널헤더값의 출처가 다르단걸 알 수 있습니다.


| 환경    | 요청헤더 출처                 |
| ----- | ----------------------- |
| 서버    | Next.js `headers()`     |
| 클라이언트 | 브라우저의 `document.cookie` |


> 단일 출처가 아니잖아



같은 값을 서로 다른 곳에서 읽고 있습니다.

이는 저희 팀내에서 트레이드 오프로 받아들인 부분인데요.

Next.js 는 서버와 클라이언트의 실행 환경이 나뉘어 있기 때문에 근본적으로 단일 출처로 설게할 수 없기 떄문입니다. 

만약 출처를 하나로 맞추는 것을 더 중요하게 본다면 서버에서 읽은 값을 클라이언트로 내려주는 방법을 고려할 수 있습니다. 루트 레이아웃에서 서버가 읽은 채널 값을 Provider 의 props 로 넘기고 클라이언트 컴포넌트는 context 로 그 값을 꺼내 쓰는 방식이에요.

```tsx
// app/layout.tsx (서버 컴포넌트)
import ChannelProvider from './ChannelProvider'

export default function RootLayout({ children }: { children: React.ReactNode }) {
  const channel = getChannelServer()

  return (
    <html>
      <body>
        <ChannelProvider channel={channel}>{children}</ChannelProvider>
      </body>
    </html>
  )
}
```

```tsx
// ChannelProvider.tsx
'use client'

import { createContext, useContext } from 'react'

const ChannelContext = createContext<string | null>(null)

export default function ChannelProvider({
  channel,
  children,
}: {
  channel: string
  children: React.ReactNode
}) {
  return <ChannelContext.Provider value={channel}>{children}</ChannelContext.Provider>
}

export const useChannel = () => {
  const channel = useContext(ChannelContext)
  if (!channel) throw new Error('ChannelProvider 안에서 사용해야 합니다')
  return channel
}
```

사용처에서는 환경에 따라 채널 값을 꺼내는 방법만 다르고 값의 출처는 서버 하나입니다.

```tsx
// 서버 컴포넌트
const { data } = await ApiServer.get('/api/products', {
  config: { [HEADER.CHANNEL]: getChannelServer() },
})

// 클라이언트 컴포넌트
const channel = useChannel()
const { data } = useQuery({
  queryKey: ['products'],
  queryFn: () => ApiClient.get('/api/products', { config: { [HEADER.CHANNEL]: channel } }),
})
```

대신 api 를 요청할 때마다 사용처에서 채널헤더를 직접 넘겨야 합니다. 

다만 이러면 재설계 목표인 "필수 헤더는 구현체 안에서 넣는다" 를 거스르게 되빈다. 기존 인터페이스의 첫 번째 문제였던 "매번 사용처에서 주입하는 필수헤더" 로 돌아가는 셈이죠.



&nbsp;

&nbsp;

&nbsp;

저희 팀은 사용처마다 필수 헤더를 넘기는 방식보다 환경별로 구현체 안에서 채널헤더를 가져오는 방식이 낫다고 판단해서 서버용 클래스와 클라이언트용 클래스를 나누기로 결정했습니다.



&nbsp;

## 인터셉터

```typescript


export const onRequest = (config: InternalAxiosRequestConfig, requestHeader: RequestHeader) => {
  const { headers } = config

  const customHeaders = new AxiosHeaders({
    ...headers,
    ...requestHeader,
  })

  return Promise.resolve({
    ...config,
    headers: customHeaders,
  })
}

export const onResponse = (res: AxiosResponse): AxiosResponse => {
  return res
}

export const onErrorResponse = (error: AxiosError | Error) => {

  if (axios.isAxiosError(error)) {

    const { status } = (error.response ?? {}) as AxiosResponse

    const responseData = error.response?.data as HttpErrorData

    throw new HttpError(status, responseData)
  }
  return Promise.reject(error)
}
```

axios 인터셉터에 등록하는 `onRequest` , `onResponse` , `onErrorResponse` 함수입니다.



여기서 `new AxiosHeaders()` 를 사용한 이유는 인터셉터가 돌려주는 config 의 `headers` 가 `AxiosRequestHeaders` 타입이기 때문인데요. 이 타입은 `AxiosHeaders` 클래스 타입을 포함해서 `set` `get` `has` `delete` 같은 메서드가 있어야 합니다.

```typescript
export type AxiosRequestHeaders = RawAxiosRequestHeaders & AxiosHeaders;
```

기존 헤더를 합쳐 일반 객체를 만들면 헤더 값만 복사되고 메서드는 복사되지 않습니다. 그래서 타입 에러가 발생하고 이를 막으려면 `as AxiosRequestHeaders` 로 타입 단언을 해야 합니다. 성능상 문제는 없겠지만 개인적으로 타입 단언을 좋아하지 않아서요.... `AxiosHeaders` 인스턴스를 그대로 사용해서 타입 단언 없이 타입이 맞도록 해봤습니다.



&nbsp;

&nbsp;

&nbsp;

`onRequest` 는 사용처에서 `config` 로 헤더를 따로 넘긴 경우 그 헤더와 인터셉터가 넣는 헤더를 합쳐서 요청에 붙입니다. `withCredentials` 같은 설정을 넣지 않은 이유는 저희 서비스에서 쓰지 않기 때문인데요. 나중에 필요해지면 이 함수에 추가하면 됩니다.



`onErrorResponse` 는 axios 에러 객체에서 에러 처리에 필요한 값을 꺼내 `HttpError` 로 만들어 던집니다.



## 에러 처리

```typescript
export interface HttpErrorData {
  code: number
  message?: string
  [key: string]: unknown
}

type DefaultHttpErrorData = Omit<HttpErrorData, 'code' | 'message'>

export default class HttpError<TData = DefaultHttpErrorData> extends Error {
  status: number
  code: number

  data?: TData

  constructor(status: number, data?: HttpErrorData) {
    super()
    this.name = 'HttpError'
    this.status = status
    const { code, message, ...rest } = data ?? {}
    this.message = message || ''
    this.code = code || 0
    this.data = rest as TData
  }
}

```

`onErrorResponse` 가 던지는 `HttpError` 는 `Error` 를 상속받은 클래스입니다. 응답 상태 코드와 서버가 내려준 에러 응답을 나눠서 담는데요.


| 필드        | 값                 |
| --------- | ----------------- |
| `status`  | HTTP 상태 코드        |
| `code`    | 서버가 내려준 에러 코드     |
| `message` | 서버가 내려준 에러 메시지    |
| `data`    | 서버가 내려준 에러 응답 데이터 |


`data` 의 타입은 제네릭 `TData` 로 정합니다. API 마다 에러 응답에 담기는 필드가 다르기 때문인데요. 사내 api 중 4xx 에러에서 `data` 값을 함께 내려주는 경우가 있어서 추가했습니다.

`HttpError` 를 만들 때도 사용처에서 최대한 편하게 쓸 수 있는 방법을 고민했는데요. 아래 두 가지 방법으로 사용성을 높였습니다.

### 1. onError 의 error 를 HttpError 로 추론하기

TanStack Query 의 기본 설정에서는 `onError` 의 `error` 가 `Error` 타입인데요. 그래서 `status` 나 `code` 를 꺼내려면 사용처마다 `instanceof` 로 타입을 좁혀야 했습니다.

```typescript
useMutation({
  mutationFn: postCoupon,
  onError: (error) => {
    if (error instanceof HttpError && error.code === 4001) {
      showToast('쿠폰 사용 한도를 넘었어요')
    }
  },
})
```

매번 확인하는 게 번거로워서 TanStack Query 의 `Register` 인터페이스로 기본 에러 타입을 `HttpError` 로 지정했습니다.

```typescript
import type HttpError from './http-error'
import '@tanstack/react-query'

declare module '@tanstack/react-query' {
  interface Register {
    defaultError: HttpError
  }
}
```

`Register` 의 `defaultError` 를 지정해 두면 `useQuery` 와 `useMutation` 이 돌려주는 `error` 와 `onError` 의 인자가 `Error` 대신 `HttpError` 타입으로 추론됩니다. 그래서 `instanceof` 없이 `status` 와 `code` 를 바로 꺼내 쓸 수 있어요.

```typescript
useMutation({
  mutationFn: postCoupon,
  onError: (error) => {
    if (error.code === 4001) {
      showToast('쿠폰 사용 한도를 넘었어요')
    }
  },
})
```

### 2. 제네릭으로 error.data 타입 지정하기

1번만 적용하면 `error.data` 의 필드 타입은 알 수 없습니다. 제네릭을 넘기지 않으면 `data` 의 필드가 모두 `unknown` 이 되는데요. `data` 의 필드까지 타입과 함께 꺼내려면 `useMutation` 의 에러 타입 자리에 `HttpError<에러 데이터 타입>` 을 넘깁니다.

```typescript
useMutation<void, HttpError<CouponErrorData>, CouponRequest>({
  mutationFn: postCoupon,
  onError: (error) => {
    if (error.code === 4001) {
      showToast(`남은 쿠폰 수는 ${error.data?.remainCount}개예요`)
    }
  },
})
```

이렇게 하면 `error.data` 가 `CouponErrorData` 타입이 되어서 `remainCount` 를 타입과 함께 꺼낼 수 있습니다.

## 싱글톤 인스턴스로 사용하기

사용처에서 요청할 때마다 http 클래스 인스턴스를 새로 생성하면 axios 인스턴스와 인터셉터도 매번 새로 만들어지는데요. 그래서 인스턴스는 한 번만 만들고 그 인스턴스를 export 해서 모든 사용처가 함께 쓰도록 했습니다.

```typescript
export default new ApiServer({
  baseUrl: API_URL,
  timeout: 5000,
  config: {
    headers: {
      [HEADER.CONTENT_TYPE]: HEADER_CONTENT.json,
    },
  },
})
```

모듈은 처음 import 될 때 한 번만 실행됩니다. 그래서 여러 파일에서 import 해도 모두 같은 인스턴스를 받아요.

아래 사용처 코드는 이 인스턴스를 import 해서 `ApiServer.get()` 처럼 바로 호출합니다.

## 사용처

새로 만든 http 인터페이스 사용방법은 아래와 같습니다. 

```typescript
export default async function getProductsApi(params: ProductsParams) {
  const { data } = await ApiServer.get<ProductsRes>('/api/products', {

  })

  return data
}
```

기존 인터페이스와 비교하면 채널헤더를 넣는 코드, 메서드 체이닝이 모두 사라지고 http 메서드, 엔드포인트url, 파라미터 딱 필요한 값만 넘기면 됩니다. 보기만해도 편안해지는군요

## 마치며

이렇게 http 인터페이스를 새로 설계해봤는데요. 좋은 인터페이스가 무엇인지 고민하며 설계했더니 팀원들의 만족도도 높았고 저도 뿌듯했습니다.

다만 모든 과정이 순조롭지는 않았어요. 운영환경과 개발환경에서 몇 가지 에러가 발생했는데요..... 눈물이 좔좔 흐르더군요. 역시 공통 인터페이스 제작의 길은 험난하기 짝이 없습니다.  트러블슈팅 과정은 별도 글로 정리할 예정입니다.
