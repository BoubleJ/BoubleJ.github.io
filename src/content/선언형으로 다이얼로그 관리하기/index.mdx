다이얼로그는 대부분의 웹사이트에서 사용되는 대표적인 UX 요소 중 하나입니다. 그만큼 웹을 구성하는 데 있어 중요도가 높고 다양한 상황에서 활용되기 때문에 관리 방식도 다양한데요. 동시에 구현과 관리가 까다로운 컴포넌트이기도 합니다.

저희 서비스의 다이얼로그는 Recoil 전역 상태로 관리되고 있었는데요. 전역 상태값으로 관리하다 보니 유지보수가 어렵고 버그 등의 문제점이 생기더라고요. 그래서 사내 서비스의 요구사항에 대응하기 쉽고 유지보수가 용이한 형태로 다이얼로그를 재설계했고 설계 과정 속에서 고민했던 부분, 설계 목적 등을 기록해 보았습니다.

# 기존 다이얼로그 — Recoil 전역 상태

기존 다이얼로그는 Recoil 전역 상태를 사용해 관리되고 있었습니다.

전역 layout.tsx 내부에서 createPortal로 모달을 렌더링하고 해당 모달의 열림 상태를 Recoil 전역 상태값으로 제어하는 구조였습니다.

```ts
const useModal = (modalId: ModalState) => {
  const [modal, setModal] = useRecoilState(modalState)
  const isOpen = modal[modalId]

  const onOpen = () => {
    setModal((current) => ({ ...current, [modalId]: true }))
    document.body.style.overflow = 'hidden'
  }

  const onClose = useCallback(() => {
    setModal((current) => ({ ...current, [modalId]: false }))
    document.body.style.overflow = ''
  }, [modalId, setModal])

  return { isOpen, onOpen, onClose }
}
```

```ts
export const modalState = atom<{
  [key in ModalState]: boolean
}>({
  key: 'modalState',
  default: {
    SIDEBAR: false,
    MAIN_POPUP_BANNER: false,
 //... 여러 키 값들 
  },
})
```

사용 예시는 다음과 같습니다.

```ts
// 노출시키고 싶은 다이얼로그 key 값을 인자로 넘겨줍니다.

  const { onClose, onOpen } = useModal('SIDEBAR')
```

## 문제점

이 방식에는 두 가지 문제점이 존재했는데요.

### 1. 다이얼로그별 Recoil key 추가 필요

새로운 화면에서 다이얼로그를 띄우기 위해서는 ModalState 타입과 modalState의 default 객체에 항목을 하나씩 추가해야 했습니다.

사용처가 늘어날수록 atom의 키 값도 계속 증가했고 각 키가 어떤 역할을 하는지 한눈에 파악하기 어려워지면서 유지보수성이 저하되는 문제가 발생했습니다.

```ts
export const modalState = atom<{
  [key in ModalState]: boolean
}>({
  key: 'modalState',
  default: {
    SIDEBAR: false,
    MAIN_POPUP_BANNER: false,
 // 키 값을 추가해야 합니다.
 //  PASSWORD : false
  },
})
```

```ts
export type ModalState =
  | 'SIDEBAR'
  | 'RECOM_GENRE'
  //타입도 추가해야 합니다.
  // | 'PASSWORD'

```

### 2. 페이지 이동 시 다이얼로그가 닫히지 않는 이슈

다이얼로그를 Recoil 전역 상태로 관리하고 있었기 때문에 다이얼로그가 열린 상태에서 뒤로 가기와 같은 페이지 이동이 발생해도 Recoil 상태값이 갱신되지 않는 문제가 있었습니다.

그 결과 페이지가 변경되었음에도 다이얼로그가 닫히지 않고 그대로 남아 있는 버그가 발생했습니다.

이러한 문제점을 개선하고자 다이얼로그 인터페이스를 재설계하기로 했습니다.



# overlay-kit + shadcn 조합으로 재설계

상술했듯이 기존 다이얼로그 로직은 별도 라이브러리 없이 직접 구현되어 있었는데요. 라이브러리를 무분별하게 도입하면 안되지만 잘 만들어지고 검증된 라이브러리를 가져와 사내 서비스에 맞게 커스터마이징한다면 더 완성도 높은 공통 컴포넌트 및 인터페이스를 설계할 수 있을 것이라 판단했습니다. 그래서 직접 구현하지 않고 잘 만들어진 라이브러리를 도입하기로 했습니다.

여러 라이브러리를 검토한 끝에 [overlay-kit](https://overlay-kit.slash.page)과 [shadcn에서 제공하는 다이얼로그 컴포넌트](https://ui.shadcn.com/docs/components/radix/dialog)를 활용해 다이얼로그를 재설계했습니다.



## shadcn 을 고른 이유



먼저 shadcn 을 고른 이유는 네 가지입니다.

첫 번째로 Next.js 와 Tailwind CSS 를 쓰는 프로젝트에서 많이 쓰이는 컴포넌트 라이브러리입니다. 커뮤니티가 활발해서 유지보수가 중단되어 deprecated 될 가능성이 낮다고 판단했습니다.

두 번째로 커스터마이징이 자유롭습니다. shadcn 은 컴포넌트를 패키지로 설치해서 쓰지 않고 CLI 로 컴포넌트 코드를 프로젝트에 복사해 오는 방식인데요. 마크업과 스타일 코드가 프로젝트 안에 있어서 서비스 디자인과 요구사항에 맞게 바꾸기 쉽습니다.

세 번째로 접근성을 직접 구현하지 않아도 됩니다. shadcn 다이얼로그는 Radix UI 를 기반으로 만들어져 있는데요. 다이얼로그 포커스 처리와 Tab 키 이동과 ESC 키 닫기 처리 같은 접근성 처리가 Radix UI 에 이미 구현되어 있습니다.

네 번째로 사내 서비스에서 이미 shadcn 을 도입하기 시작한 상태였습니다. 여러 컴포넌트 라이브러리를 함께 쓰기보다는 하나로 통일하는 편이 낫다고 판단했어요.



## overlay-kit 을 고른 이유

overlay-kit 을 고른 이유는 두 가지입니다.

첫 번째로 오버레이를 선언적으로 관리합니다. 사용처는 열림 상태를 state 로 들고 있지 않고 `overlay.open` 에 띄울 요소만 넘기면 됩니다. overlay-kit 은 넘겨받은 함수에 `isOpen` 과 `close` 를 넘겨 호출만 담당할 뿐 그 요소가 다이얼로그인지 바텀시트인지는 확인하지 않는데요. 오버레이를 열고 닫는 로직과 오버레이 UI 가 분리되어 있어서 다이얼로그와 바텀시트 등 다양한 오버레이 컴포넌트를 동일한 방식으로 띄울 수 있습니다.

두 번째로 여러 오버레이를 겹쳐 띄울 수 있습니다. overlay-kit 은 연 순서대로 오버레이 id 를 배열에 쌓고 그 순서대로 렌더링합니다. 그래서 오버레이를 띄운 순서대로 화면에 쌓이는 것을 보장할 수 있죠.



## shadcn 다이얼로그 제작



shadcn 다이얼로그 공식 문서의 사용 예시는 아래와 같습니다. 

```ts
import { Button } from "@/components/ui/button"
import {
  Dialog,
  DialogClose,
  DialogContent,
  DialogDescription,
  DialogFooter,
  DialogHeader,
  DialogTitle,
  DialogTrigger,
} from "@/components/ui/dialog"
import { Field, FieldGroup } from "@/components/ui/field"
import { Input } from "@/components/ui/input"
import { Label } from "@/components/ui/label"

export function DialogDemo() {
  return (
    <Dialog>
      <form>
      // 다이얼로그 트리거 컴포넌트
        <DialogTrigger asChild>
          <Button variant="outline">Open Dialog</Button>
        </DialogTrigger>
        <DialogContent className="sm:max-w-sm">
          <DialogHeader>
            <DialogTitle>Edit profile</DialogTitle>
            <DialogDescription>
              Make changes to your profile here. Click save when you&apos;re
              done.
            </DialogDescription>
          </DialogHeader>
          <DialogFooter>
            <DialogClose asChild>
              <Button variant="outline">Cancel</Button>
            </DialogClose>
            <Button type="submit">Save changes</Button>
          </DialogFooter>
        </DialogContent>
      </form>
    </Dialog>
  )
}

```

컴파운드 컴포넌트 패턴으로 다이얼로그 구조를 잡고 `DialogTrigger`로 열기까지 라이브러리가 처리해 주어 그대로 가져다 쓰기 편합니다. 다만 위 예시는 **비제어(Uncontrolled)** 방식입니다. `DialogTrigger`에 의해 내부에서 열림/닫힘이 관리되므로 부모에서 `open` 상태를 제어하지 않습니다.

저희 서비스에서는 다이얼로그를 **제어 컴포넌트(Controlled)** 형태로 쓰는 편이 더 맞다고 판단했습니다. overlay-kit 이 다이얼로그 컴포넌트에 `isOpen` 과 `close` 를 넘겨서 열림 상태를 바깥에서 제어하기 때문입니다. 그래서 shadcn 다이얼로그의 기반인 Radix UI 의 [공식 문서](https://www.radix-ui.com/primitives/docs/components/dialog#examples)에서 제어 방식 사용 예시를 찾았습니다.

```ts
import * as React from "react";
import { Dialog } from "radix-ui";

const wait = () => new Promise((resolve) => setTimeout(resolve, 1000));

export default () => {
	const [open, setOpen] = React.useState(false);

	return (
		<Dialog.Root open={open} onOpenChange={setOpen}>
			<Dialog.Trigger>Open</Dialog.Trigger>
			<Dialog.Portal>
				<Dialog.Overlay />
				<Dialog.Content>
					<form
						onSubmit={(event) => {
							wait().then(() => setOpen(false));
							event.preventDefault();
						}}
					>
						{/** some inputs */}
						<button type="submit">Submit</button>
					</form>
				</Dialog.Content>
			</Dialog.Portal>
		</Dialog.Root>
	);
};

```

`open`과 `onOpenChange`를 넘기면 state 기반의 제어 컴포넌트 형식으로 사용할 수 있습니다. 이 방식을 참고해 shadcn 다이얼로그를 한 겹 감싼 래퍼 컴포넌트를 만들고 `open` / `onClose`로 노출을 제어하도록 설계했습니다. 구현한 래퍼는 아래와 같습니다.

```tsx

function Dialog({ open, onClose, className, children }: PropsWithChildren<DialogProps>) {
  const handleOpenChange = (open: boolean) => {
    if (!open) {
      onClose()
    }
  }
  return (
    // 외부에서 넘겨받은 상태값과 핸들러를 주입
    <DialogComponent open={open} onOpenChange={handleOpenChange}>
      <DialogContent
       //..
        onClick={onClose}
      >
        {children}
      </DialogContent>
    </DialogComponent>
  )
}

export { Dialog, DialogTitle, DialogButtonFooter, DialogButton, DialogDescription }

```

이 래퍼와 함께 다이얼로그 제목을 나타내는 `DialogTitle` 과 본문을 나타내는 `DialogDescription` 과 버튼 영역을 나타내는 `DialogButtonFooter` 와 `DialogButton` 을 만들었습니다. 이 블록들을 조합해 실제로 노출할 다이얼로그 컴포넌트를 만듭니다. 예를 들어 확인 다이얼로그는 아래처럼 만들 수 있습니다.

```tsx
export default function ConfirmDialog({ open, onConfirm, message, title, buttonText = '확인' }: ConfirmDialogProps) {
  return (
    <Dialog open={open} onClose={onConfirm}>
      <DialogTitle title={title} />
      <DialogDescription>
        <p>{message}</p>
      </DialogDescription>
      <DialogButtonFooter>
        <DialogButton text={buttonText} onClick={onConfirm} />
      </DialogButtonFooter>
    </Dialog>
  )
}
```

## 접근성 트러블슈팅

Radix UI 의 접근성 처리 덕분에 구현 중에 놓친 부분을 발견하기도 했습니다.

사내 다이얼로그 디자인 시안은 다이얼로그 제목이 있는 케이스, 없는 케이스 둘 다 존재했는데요. 그래서 제목이 있을 때만 shadcn의 `DialogTitle`을 사용했는데 개발 중 콘솔에 에러가 찍히는 것을 발견했습니다.

![다이얼로그웹접근성](<./다이얼로그웹접근성.png>)

에러 내용을 보니 Radix 다이얼로그를 쓸 때는 **반드시 `DialogTitle`을 포함**해야 한다는 요구사항이었습니다. 스크린 리더 사용자를 위해 다이얼로그에 제목이 있어야 한다는 Radix 라이브러리의 접근성 설계 때문입니다.

다만 앞서 말한 대로 제목을 노출하지 않는 다이얼로그도 있었습니다. 이 경우 `VisuallyHidden`을 사용해 해결했습니다. `DialogTitle`을 `VisuallyHidden`으로 감싸면 화면에는 보이지 않으면서 스크린 리더에만 읽히도록 할 수 있습니다.

```tsx

// title이 없으면 시각적으로 숨기고 스크린 리더에만 노출
function DialogTitle({ title, className }: DialogTitleProps) {
  if (!title) {
    return (
      <VisuallyHidden>
        <DialogTitleComponent >
          Dialog
        </DialogTitleComponent>
      </VisuallyHidden>
    )
  }

  return (
    <DialogHeader>
      <DialogTitleComponent >
        {title}
      </DialogTitleComponent>
    </DialogHeader>
  )
}

```

```tsx
// title 을 넘기지 않으면 VisuallyHidden 으로 감싼 제목이 그려집니다
<ConfirmDialog open={isOpen} onConfirm={close} message="저장되었습니다." />
```

이렇게 제목 유무에 따라 `DialogTitle`을 보이거나 `VisuallyHidden`으로 감싸는 방식으로 웹 접근성까지 고려한 다이얼로그 컴포넌트를 구성할 수 있었습니다. 

## 오버레이 훅 제작

다이얼로그 UI 를 만들었으니 이제 overlay-kit 으로 다이얼로그를 띄워 보겠습니다.

### OverlayProvider 연결

overlay-kit 을 쓰려면 앱 최상단을 `OverlayProvider` 로 감싸야 합니다. 저희는 `DialogProvider` 컴포넌트를 만들어 루트 layout.tsx 에서 감쌌습니다.

```tsx
export default function DialogProvider({ children }: PropsWithChildren) {
  return <OverlayProvider>{children}</OverlayProvider>
}
```

`OverlayProvider` 를 바로 쓰지 않고 한 번 감싼 이유는 뒤에서 다룰 앱 백키 처리와 라우트 전환 처리를 이 컴포넌트 안에 넣기 위해서입니다.

### useOverlay 훅

overlay-kit 의 `overlay` 객체를 사용처에서 바로 쓸 수도 있습니다. 하지만 다이얼로그를 닫을 때마다 해야 하는 처리가 있어서 `useOverlay` 훅으로 한 번 감쌌습니다.

```tsx
type RenderProps = Pick<ComponentProps<OverlayAsyncControllerComponent<void>>, 'isOpen' | 'close'>

type OpenOverlay = (createOverlayElement: (props: RenderProps) => JSX.Element) => Promise<void>
```

`RenderProps` 는 다이얼로그 컴포넌트가 받는 `isOpen` 과 `close` 의 타입입니다. 직접 정의하지 않고 overlay-kit 타입에서 꺼내 썼는데요. overlay-kit 이 타입을 바꾸면 이 타입도 같이 바뀌고 맞지 않는 곳은 훅이나 사용처에서 컴파일 에러로 드러납니다.

```tsx
const CLOSE_ANIMATION_DURATION = 300

export default function useOverlay() {
  const open: OpenOverlay = (createOverlayElement) => {
    return overlay.openAsync<void>(({ isOpen, close, overlayId }) => {
      const handleClose = () => {
        close()
        setTimeout(() => overlay.unmount(overlayId), CLOSE_ANIMATION_DURATION)
      }

      return createOverlayElement({ isOpen, close: handleClose })
    })
  }

  return { open }
}
```

`open` 은 다이얼로그 요소를 만드는 함수를 받습니다. 이 함수는 `isOpen` 과 `close` 를 인자로 받아 다이얼로그 컴포넌트에 넘깁니다.

### 닫기 애니메이션 처리

`handleClose` 는 `close` 를 호출한 다음 300ms 뒤에 `overlay.unmount` 를 호출하도록 구현했는데요. 왜 바로 unmount 하지 않았을까요?

overlay-kit 의 `close` 는 `isOpen` 을 false 로 바꾸기만 하고 요소는 언마운트되지 않습니다. 이때 shadcn 다이얼로그의 닫기 애니메이션이 처리되는데요. `close` 와 같은 시점에 `unmount` 를 호출하면 요소가 바로 언마운트되어 애니메이션이 보이지 않고 화면에서 뚝 사라집니다.

그렇다면 `unmount` 를 호출하지 않고 `close` 만 호출하면 되지 않을까요?

`close` 만 호출하면 화면에서는 다이얼로그가 닫히지만 다이얼로그 요소는 `OverlayProvider` 안에 그대로 남아 있습니다. 그래서 다이얼로그를 열 때마다 닫힌 요소가 계속 쌓입니다. 이 문제를 막으려고 `close` 와 `unmount` 를 함께 써서 `close` 를 호출하고 닫힘 애니메이션이 끝나는 0.3초 뒤에 `unmount` 를 호출하도록 구현했습니다. 이 처리는 모든 오버레이에 동일하게 적용되어야 하니 훅 내부에서 처리하도록 했습니다.

### 사용처

```tsx
const overlay = useOverlay()

const openConfirmDialog = () => {
  overlay.open(({ isOpen, close }) => (
    <ConfirmDialog open={isOpen} onConfirm={close} message="저장되었습니다." />
  ))
}
```

사용처는 열림 상태를 state 로 들고 있지 않습니다. 열림 상태는 overlay-kit 의 `OverlayProvider` 가 따로 관리하기 때문이죠.

`open` 은 Promise 를 반환하고 `close` 가 호출되면 resolve 됩니다. 그래서 다이얼로그가 닫힌 다음에 실행할 로직은 `await` 뒤에 쓰면 됩니다.

```tsx
await overlay.open(({ isOpen, close }) => (
  <ConfirmDialog open={isOpen} onConfirm={close} message="비밀번호가 변경되었습니다." />
))

router.push('/login')
```

## shadcn drawer 로 바텀시트 만들기

다이얼로그 다음으로 많이 쓰는 오버레이가 바텀시트였는데요. 바텀시트는 shadcn 의 Drawer 컴포넌트로 만들고 다이얼로그와 같은 `useOverlay` 로 띄우도록 설계했습니다.

shadcn Drawer 는 vaul 라이브러리를 기반으로 만들어져 있고 vaul 은 내부에서 Radix UI 의 Dialog 를 사용합니다. 그래서 다이얼로그처럼 `open` 과 `onOpenChange` 를 넘겨 제어 컴포넌트로 쓸 수 있습니다.

### BottomSheet 래퍼

```tsx
const BottomSheetCloseContext = createContext<(() => void) | null>(null)

function BottomSheet({ open, onClose, children }: PropsWithChildren<BottomSheetProps>) {
  const handleOpenChange = (open: boolean) => {
    if (!open) {
      onClose()
    }
  }

  return (
    <BottomSheetCloseContext.Provider value={onClose}>
      <DrawerComponent open={open} onOpenChange={handleOpenChange} direction="bottom">
        <DrawerContent>{children}</DrawerContent>
      </DrawerComponent>
    </BottomSheetCloseContext.Provider>
  )
}
```

`Dialog` 래퍼와 같은 형태로 구현했습니다. vaul 은 딤을 클릭하거나 바텀시트를 아래로 끌어내리면 `onOpenChange(false)` 를 호출하는데요. 이때 `handleOpenChange` 가 바깥에서 넘겨받은 `onClose` 를 호출하도록 했습니다.

shadcn 공식 예시는 `DrawerTrigger` 버튼으로 바텀시트를 엽니다. 하지만 이미 오버레이를 띄우는 `useOverlay` 훅을 만들어 두었기 때문에 바텀시트도 `DrawerTrigger` 대신 제어 컴포넌트 형식으로 만들어 `overlay.open` 으로 똑같이 열도록 했습니다.

### 닫기 버튼과 Context

바텀시트 안쪽 블록에서도 `onClose` 가 필요한 경우가 있었는데요. 제목 옆 닫기 버튼처럼 바텀시트를 닫는 요소가 생길 때마다 `onClose` 를 props 로 넘기면 props drilling 이 생깁니다. 그래서 `BottomSheet` 가 받은 `onClose` 를 Context 로 감싸 주입하도록 설계했습니다.

```tsx
function BottomSheetTitle({ title, showCloseButton }: BottomSheetTitleProps) {
  const onClose = useContext(BottomSheetCloseContext)

  if (!title) {
    return (
      <VisuallyHidden>
        <DrawerTitleComponent>바텀시트</DrawerTitleComponent>
      </VisuallyHidden>
    )
  }

  return (
    <DrawerHeader>
      <DrawerTitleComponent>{title}</DrawerTitleComponent>
      {showCloseButton && onClose && (
        <button type="button" onClick={onClose}>
          <Icon type="IcoClose" title="닫기" />
        </button>
      )}
    </DrawerHeader>
  )
}
```

`BottomSheetTitle` 은 Context 에서 `onClose` 를 꺼내 닫기 버튼에 연결합니다. 사용처는 `showCloseButton` 만 넘기면 됩니다.

제목이 없을 때 `VisuallyHidden` 으로 감싼 제목을 그리도록 한 이유는 다이얼로그와 같습니다. vaul 이 Radix UI Dialog 를 사용하기 때문에 바텀시트에도 제목이 반드시 있어야 하거든요.

### 바텀시트 사용처

```tsx
export default function ComicListBottomSheet({ open, close }: ComicListBottomSheetProps) {
  return (
    <BottomSheet open={open} onClose={close}>
      <BottomSheetTitle title="만화 리스트" showCloseButton />
      <BottomSheetDescription />
      {/* 장르 링크 목록 */}
    </BottomSheet>
  )
}
```

```tsx
overlay.open(({ isOpen, close }) => <ComicListBottomSheet open={isOpen} close={close} />)
```

다이얼로그와 같은 방법으로 띄웁니다. overlay-kit 은 넘겨받은 요소가 다이얼로그인지 바텀시트인지 확인하지 않기 때문에 `useOverlay` 를 고치지 않고 바텀시트를 띄울 수 있었습니다.
